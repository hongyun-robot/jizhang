# identity/user-auth Specification

## Purpose

让用户安全地登录自用记账站点并维持会话有效，覆盖双 token 认证、刷新轮换、失败限流与停用账号的访问拒绝。

## Requirements

### Requirement: 用户名密码登录

系统 SHALL 支持用户名 + 密码登录，成功后按设备类型建立会话并签发短期 access token 与长期 refresh token；失败时 MUST 返回统一错误提示，不泄露账号是否存在。默认 access token 有效期 SHALL 为约 30 分钟；refresh token 默认 SHALL 在每次成功刷新后重新获得约 30 天有效期，不增加绝对登录时长上限，已有有效期配置 SHALL 继续生效。

#### Scenario: 登录成功
- **WHEN** 用户提交正确的用户名和密码
- **THEN** 系统返回 access token（默认约 30 分钟有效）并设置 refresh token（默认约 30 天有效），前端据此进入应用

#### Scenario: 凭据错误
- **WHEN** 用户提交错误的用户名或密码
- **THEN** 系统返回统一的“用户名或密码错误”提示

#### Scenario: 持续使用延长登录
- **WHEN** 会话仍有效，用户在刷新期限内成功刷新令牌
- **THEN** 同一会话的 refresh 有效期从本次成功刷新起再延长约 30 天，其他会话的有效期不变化

### Requirement: token 刷新轮换

系统 SHALL 在 access token 过期且会话仍有效时允许用 refresh token 换取新 token；refresh 凭据 MUST 存储于服务端 Redis，且新签发后同一旧 refresh token MUST 立即失效（轮换）。轮换 MUST 原子执行，MUST NOT 使一次旧凭据产生多个有效后继，也 MUST NOT 改变会话的设备类型。客户端收到可刷新的 401 后 MUST 实际刷新或使用同一会话中已经完成刷新的新 token，MUST NOT 将被拒绝的旧 token 当作刷新结果；明确的会话撤销或替换 MUST 直接结束本地会话，不调用全设备退出。一个浏览器共享会话内针对同一旧 token 的并发请求 SHALL 协调刷新并共享结果，每个原请求 MUST 最多重试一次；重试 SHALL 保留原请求内容与操作标识。并发输掉轮换的请求 MUST NOT 清除胜出请求设置的有效 Cookie，不得使正常并发演变为账号级撤销。403 MUST NOT 触发刷新；暂时网络或服务错误 MUST 保留可重试状态。

#### Scenario: 用过期 access token 请求
- **WHEN** 客户端携带过期 access token 调用受保护接口且服务端会话仍有效
- **THEN** 接口返回可刷新的 401，客户端自动用 refresh token 换新 token 后重试，用户无感知

#### Scenario: refresh token 失效
- **WHEN** refresh token 已过期或已被轮换作废，且无法从同一浏览器的有效刷新结果恢复
- **THEN** 刷新请求失败，客户端清理该失效会话并跳转登录页，不循环刷新，不调用全设备退出，不影响其他会话

#### Scenario: 并发请求同时过期
- **WHEN** 同一页面会话中的多个请求携带同一个过期 access token 返回 401
- **THEN** 只执行一次刷新，所有可重试请求使用新 token 且各自最多重试一次

#### Scenario: 刷新后迟到的旧请求
- **WHEN** 新 token 已生效后，另一个携带旧 token 的在途请求才返回 401
- **THEN** 该请求直接使用当前会话的新 token 重试，不再次轮换 refresh token

#### Scenario: 重试仍然未授权
- **WHEN** 原请求使用新 token 重试后仍返回 401
- **THEN** 客户端结束会话并展示登录入口，不发起第二次重试，也不撤销其他设备

#### Scenario: 资金请求的认证重试
- **WHEN** 带操作标识的资金请求因 token 过期被拒绝，刷新后重新发送
- **THEN** 重试保留相同操作标识与提交内容，不将认证重试解释为新的资金操作

#### Scenario: 权限不足
- **WHEN** 已登录用户请求无权限资源并收到 403
- **THEN** 展示权限错误且不调用刷新接口

#### Scenario: 多标签页同时恢复或刷新
- **WHEN** 共享 Cookie 的多个标签页同时打开或遇到 access token 过期
- **THEN** 客户端协调轮换并使用有效结果，各标签页正常恢复；服务端的并发冲突不得清除有效 Cookie、替换会话或撤销其他设备

#### Scenario: 旧刷新成功响应与新登录交错
- **WHEN** 同浏览器旧会话的刷新已发送但响应尚未结算，另一个标签页发起新登录
- **THEN** 认证写入按顺序完成，旧刷新成功响应不能晚于新登录而覆盖其 Cookie，最终恢复的是新登录会话

#### Scenario: 无法建立可靠的标签页协调
- **WHEN** 浏览器无法提供可靠的共享认证请求串行机制
- **THEN** 客户端暂停认证写入并显示明确的恢复提示，不并行发送可能覆盖有效 Cookie 的登录、刷新或退出请求，不声称已有会话被撤销

### Requirement: 登录失败限流
系统 SHALL 基于 Redis 对同一用户名与同一来源 IP 的连续登录失败计数，超过阈值（如 5 次）后在冷却期（如 10 分钟）内拒绝该用户的登录尝试。

#### Scenario: 暴力破解防护
- **WHEN** 同一用户名连续登录失败达到阈值
- **THEN** 冷却期内该用户的登录请求被直接拒绝并提示稍后再试

### Requirement: 停用账号拒绝访问
被管理员停用的账号 MUST 无法登录，其此前签发的 token 在服务端校验时 MUST 被拒绝。

#### Scenario: 停用后登录
- **WHEN** 停用账号提交正确凭据
- **THEN** 登录失败并提示账号已停用

#### Scenario: 停用后的在线会话
- **WHEN** 停用前已登录的会话继续携带有效 token 请求
- **THEN** 服务端校验时发现停用状态并返回 401，会话立即失效

### Requirement: 登出

系统 SHALL 提供含义明确的“退出所有设备”入口；用户主动退出成功后，该账号在手机、平板、电脑上此前建立的全部 access token 与 refresh token MUST 立即失效。全设备退出 MUST 验证发起者仍持有当前有效会话的凭据；无凭据、无效凭据或被替换会话 MUST NOT 撤销后续新登录或其他会话。自然到期、被替换、刷新失败等被动结束 MUST 仅清理对应客户端状态，MUST NOT 调用全设备退出。客户端结束会话或切换登录账号时 MUST 清理前一会话的数据缓存、导航筛选记忆和未提交业务草稿；前一会话的迟到读取或刷新结果 MUST NOT 恢复已退出的客户端会话、写入新账号状态或展示前一账号的个人数据。外观主题选择 SHALL 保持既有持久化行为。同浏览器标签页 SHALL 同步结束会话；其他设备 SHALL 在下一次请求或回到前台校验时展示失效，无需跨设备实时推送。此处立即失效 SHALL 指撤销成功后开始认证的新请求被拒绝，撤销前已经通过认证的资金操作仍按原有事务与幂等规则完成。

#### Scenario: 用户登出
- **WHEN** 仍持有效会话的用户点击“退出所有设备”且服务端撤销成功
- **THEN** 该账号所有既有会话不能继续访问或刷新，当前浏览器全部标签页清理业务状态并进入登录页，其他账号不受影响

#### Scenario: 登出期间刷新返回
- **WHEN** token 刷新或会话恢复尚未结束时用户主动退出，随后旧请求返回成功
- **THEN** 客户端仍保持登出状态，旧结果不重新设置 token、用户或业务草稿，服务端已撤销的会话不恢复

#### Scenario: 换号后的迟到读取
- **WHEN** 用户从账号甲切换到账号乙后，账号甲的个人负债请求才返回
- **THEN** 账号乙的页面与缓存不展示账号甲的个人负债结果

#### Scenario: 同一账号重新登录
- **WHEN** 用户退出后再次登录同一账号
- **THEN** 不自动恢复上一会话的未提交草稿或导航记忆，用户主动打开的站内链接仍可恢复其显式查询条件

#### Scenario: 被替换设备尝试全设备退出
- **WHEN** 旧手机会话被新手机替换后，旧会话提交迟到的退出请求
- **THEN** 不撤销新手机、电脑或平板会话，旧客户端只清理自身失效状态

#### Scenario: 退出成功响应与重新登录交错
- **WHEN** 当前浏览器的退出请求尚未结算，另一个标签页尝试重新登录
- **THEN** 新登录等待此前退出响应结算后再发送，旧退出响应不能删除新登录的 Cookie，旧本地清理事件不能结束新会话

#### Scenario: 全设备退出请求暂时失败
- **WHEN** 主动退出因网络或服务暂不可用而未获得撤销成功确认
- **THEN** 当前浏览器清理本地业务状态并阻止自动恢复旧会话，明确提示尚未确认其他设备退出且可重试，不显示全设备退出成功

### Requirement: 按设备类型并行登录

系统 SHALL 将登录会话自动归为手机、平板、电脑三类；每个账号每类 MUST 最多存在一个有效会话，三类 SHALL 可同时在线。设备类型 SHALL 根据浏览器提供的信息判断，无法识别时归入电脑；类型信息 MUST NOT 被当作可信硬件身份或访问权限。新登录凭据校验及会话建立成功后，系统 MUST 原子替换同账号同类型的旧会话，MUST NOT 影响其他类型或其他账号。不同浏览器、不同浏览器配置和无痕窗口 SHALL 分别建立会话并遵守相同类型的单会话规则；同一 Cookie 存储空间内的标签页 SHALL 共享一个会话。

#### Scenario: 三类设备同时在线
- **WHEN** 同一账号先后在手机、平板和电脑正确登录
- **THEN** 三个会话均可访问和刷新，各自刷新不挤掉其他类型

#### Scenario: 同类新登录替换旧登录
- **WHEN** 手机甲已有有效会话，手机乙用同一账号成功登录
- **THEN** 手机甲的 access token 与 refresh token 均立即失效，手机乙可使用，平板和电脑继续在线

#### Scenario: 同一电脑换浏览器登录
- **WHEN** 同一账号已经在电脑 Chrome 登录，随后在 Edge 或另一个独立浏览器配置中成功登录
- **THEN** 新电脑类会话替换旧电脑类会话，不能因来自同一台硬件而同时保留

#### Scenario: 同类型并发登录
- **WHEN** 同一账号的两个同类型登录并发完成
- **THEN** 按服务端成功提交会话的顺序决定最终会话，最后提交者有效，最终最多保留一个该类型会话

#### Scenario: 新登录失败
- **WHEN** 新登录凭据错误、账号受限或会话建立失败且尚未提交
- **THEN** 不因该失败尝试替换已有会话，凭据错误仍使用统一提示

#### Scenario: 自动识别与未知浏览器
- **WHEN** 浏览器信息可识别为手机或平板，或信息不足无法识别
- **THEN** 前者分别占用手机或平板名额，后者占用电脑名额；不显示手动类型选择，不以屏幕窗口大小改变已建立会话的类型

### Requirement: 会话即时撤销与失效隔离

系统 MUST 在受保护请求和刷新时校验独立会话是否仍有效，MUST NOT 仅依赖 access token 的签名与到期时间。被同类新登录替换、自然到期或已撤销的会话 MUST 不能继续访问或刷新；此类会话失效 MUST NOT 撤销其他会话。无效刷新凭据 MUST NOT 仅凭其中的账号或会话标识触发撤销，MUST NOT 破坏同类型后续新登录。管理员重置密码、停用、角色调整 SHALL 继续使目标账号全部设备会话失效，恢复账号 MUST NOT 恢复已撤销令牌。服务端无法验证撤销状态时 MUST 拒绝执行受保护操作，返回可重试的服务错误，MUST NOT 放行或误当成全账号盗用。

#### Scenario: 被替换会话继续调用
- **WHEN** 旧电脑会话被新电脑登录替换后，仍携带未到期的 access token 请求或旧 refresh token 刷新
- **THEN** 请求被拒绝，客户端显示会话已失效；可识别替换原因时提示同类设备已登录，新电脑和其他类型继续可用

#### Scenario: 单个会话自然过期
- **WHEN** 手机会话的刷新有效期结束，电脑和平板会话仍有效
- **THEN** 手机不能访问或恢复登录，电脑和平板仍可访问和刷新

#### Scenario: 伪造或重放无效刷新凭据
- **WHEN** 客户端提交伪造账号前缀、未知、过期或已轮换的 refresh token
- **THEN** 无效凭据不能换取令牌，不按未经验证的账号标识吊销其他会话，也不使已经成功刷新的当前凭据失效

#### Scenario: 管理员执行安全操作
- **WHEN** 管理员重置密码、停用或调整用户角色时，该用户手机、平板、电脑均在线
- **THEN** 该用户全部既有 access token 与 refresh token 失效；角色调整后的新登录按新权限执行，停用期间不能登录，恢复后仍须重新登录

#### Scenario: 撤销与刷新交错
- **WHEN** 某会话正在刷新或登录，同时发生针对该会话的同类替换或账号级撤销
- **THEN** 按成功提交顺序执行，撤销前建立的会话不能被迟到刷新复活；撤销后凭当前有效凭据重新提交的新登录可建立新会话

#### Scenario: 认证状态服务暂不可用
- **WHEN** 服务端无法读取或更新可信的会话撤销状态
- **THEN** 受保护操作不执行，客户端收到可重试服务错误，不声称登录已失效或所有设备已退出，不撤销其他会话

#### Scenario: 其他设备回到前台
- **WHEN** 会话在后台期间被替换或全设备撤销，用户随后切回应用
- **THEN** 客户端重新校验会话；失效则清理业务状态并显示登录入口，暂时网络失败则显示可重试状态，不能继续以旧身份提交业务

### Requirement: 新会话机制切换

新会话机制上线后，旧机制签发的 access token 与 refresh token MUST 统一失效，用户 SHALL 重新登录一次。旧凭据的恢复或刷新请求 MUST NOT 撤销升级后已经建立的新会话；重新登录后 SHALL 使用设备分组和即时撤销规则。

#### Scenario: 旧登录升级后恢复
- **WHEN** 用户携带升级前的令牌访问或刷新
- **THEN** 系统拒绝旧凭据并引导重新登录，不提供继续使用旧令牌的兼容窗口

#### Scenario: 旧客户端迟到刷新
- **WHEN** 新机制会话已建立，旧客户端随后提交升级前的 refresh token
- **THEN** 旧请求失败，不影响任何新机制会话

#### Scenario: 未更新的登录页面
- **WHEN** 升级前仍打开的页面以旧认证协议提交登录
- **THEN** 系统提示刷新页面，不建立会话或写入可能干扰新版标签页的 Cookie
