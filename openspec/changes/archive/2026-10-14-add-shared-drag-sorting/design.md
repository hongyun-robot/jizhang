## Context

动机见 `proposal.md`；行为契约见四份 delta specs。本方案基于当前工作区，包含已归档但尚未提交的个人平台 / 商家改动，不回退到旧共享目录。

- `CategoryRepo.List`、分类树组装和 `AccountRepo.Metadata` 已按 `sort, id` 提供稳定顺序。分类管理是响应式大类卡片网格，子分类目前为可改名 / 删除的 Tag，没有子分类管理弹窗；账户管理分别使用手机列表和桌面 Ant Design Table。
- 分类更新 handler 把省略的 `sort` 变成 0；账户更新也丢失字段是否提供的区别。`AccountEditor` 显示数值排序字段并随资料一起提交，`PersonalLiabilityAccountModal` 也提交缓存中的位置或默认 10。这些路径可能覆盖新的排序结果。
- `VoucherPlatform` 没有排序字段，后端列表及 `platformCache.ts` 均按精确名称排序。平台管理已有包含搜索，业务 `PlatformInput` 按目录顺序过滤和映射。
- 三类目录均按本人归属隔离，全部有效登录角色可维护。写入普遍使用 `repository.LedgerWrite` 的全账本锁及事务，账户创建另有按 owner / request_key 的持久化摘要和重试保护。
- 客户端使用按 auth epoch 划分的 React Query key；平台目录已有显式 `_epoch` 和取消旧读取后更新缓存的保护。账户列表会定时重取，排序状态不能直接依赖每次查询返回的对象数组。

## Goals / Non-Goals

**Goals:**

- 让通用层负责手势、可访问性、预览和保存状态，业务层仅提供稳定 ID、完整列表及明确作用域。
- 让三个业务接口共用顺序协议和校验，保持归属与分类层级校验可审查。
- 复用现有排序列、认证范围和事务入口，按批处理保存，只写目录位置。
- 对拖动、普通资料维护及业务选项建立同一顺序来源，同时保留账户建户重试与资金约束。

**Non-Goals:**

- 不建立任意表名 / 资源名的外部通用写接口，不把业务权限藏在动态反射中。
- 不做分类跨父级移动、跨收支类型移动或账户类型分组排序，不新增目录历史版本管理。
- 不让业务选择器承担排序和分类维护，不改变统计图表按金额或时间排序的规则。
- 不改写已有个人目录迁移 `000015`，本次规划不执行迁移或部署。

## Decisions

### 1. 分别暴露业务接口，共用请求和事务内顺序机制

新增以下接口，并接在现有认证路由组中，沿用全部有效登录角色的本人目录权限：

| 接口 | 作用域 | 额外字段 |
| --- | --- | --- |
| `PUT /api/v1/categories/reorder` | actor + kind + parent_id | `kind` 必填；一级用 `parent_id: null`，子分类用真实一级 ID |
| `PUT /api/v1/accounts/reorder` | actor 的全部资金账户 | 无；包含基金、负债和停用账户 |
| `PUT /api/v1/voucher-platforms/reorder` | actor 的完整个人商家目录 | 无 |

统一请求为 `{ ordered_ids: number[], previous_ids: number[], request_key: string }`，分类接口另带上表字段。统一成功 data 为 `{ ordered_ids: number[] }`，沿用现有 `{code, message, data}` 包装。空数组仅在当前作用域确实为空时合法；界面少于两项不提供无意义排序。`owner_id` 不作为作用域输入。

共享顺序模块只处理真实 ID 的排列验证、基准比较和位置分配；各 service 明确加载并校验当前业务作用域，各 repository 以 owner 及分类 kind / parent 条件执行位置更新。表和模型由代码内适配器确定，不能从请求获得。批量 SQL 可以用参数化 CASE 或事务内逐行 update；后者也只有一个 API 请求和一次提交，不调用已有资料更新 service。

选择三个薄业务接口而非通用 `/reorder/:resource`：归属、父分类合法性和路由权限仍清楚可见，复用的是排列与事务机制。选择批量请求而非循环调用原 CRUD：原接口涉及名称、期初和账单配置，且多请求无法原子提交。

### 2. 在现有锁内核对完整基准，抵御并发和迟到重试

使用现有 `LedgerWrite` 入口与目录维护共享序列化边界，不另起与 CRUD 无关的锁。排序接口不隐式初始化目录：在锁内确认相应个人初始化标记已经完成，未完成返回 409 并要求先读取列表。现有目录 GET 负责初始化，因此管理页加载后可提供完整基准；非法排序请求不会生成默认条目或改变初始化标记，也不产生嵌套写事务。

事务内按以下顺序处理：

1. 校验两数组必须存在、每项为正整数、无重复、两者为同一 ID 集合；分类 kind / parent 结构合法。
2. 校验 parent 及请求中条目的存在性和本人归属。跨账号返回 403，不存在目标返回 404；本人条目不属于该分类作用域返回 400。
3. 使用锁内最新的目录元数据按 `sort, id` 获取完整列表；数量和成员必须完全一致，漏项 / 新增冲突返回 409，不能只根据提交长度更新部分目录。
4. 在个人作用域中读取 `request_key` 的持久化结果；已有键只在输入摘要相同且当前仍等于该键目标时成功，否则返回 409。新键在当前已等于目标时记录结果并成功；其他情况要求当前顺序等于 `previous_ids`。客户端每次新拖动生成新键，重试复用原键。
5. 分配连续 `sort = 0..n-1` 并写入全部条目，和成功请求摘要一起提交；任一失败全部回滚，提交后才执行必要的既有服务端显示缓存失效。

基准包含顺序而非仅数量，所以两个设备重排相同条目也会检测冲突。目录名称或账户余额变化不影响基准，不无端阻止排序。响应丢失可重试原 payload；已经有后续不同排序时，旧 payload 不能覆盖它。404 / 409 均让前端重取当前列表后重新调整。

备选为 last-write-wins 或独立 revision 表：前者会静默覆盖其他设备，后者增加额外状态维护。目录已是完整小列表，不引入 revision 表或操作队列；但实施的 MySQL 并发测试证明仅基准数组不能检测顺序改回后的旧请求重放，因此增加 `catalog_order_requests`，按 owner / scope / request_key 保存成功摘要，拒绝旧键重新执行。

### 3. 复用排序列，并明确省略字段和追加规则

分类与账户保留现有 `sort`，普通读取继续稳定按 `sort, id`，不迁移重写其旧顺序。`VoucherPlatform` 增加整型 `sort` 及 JSON 字段，读取改为 `sort, id`，增加 `(owner_id, sort, id)` 索引。

创建时若客户端省略排序位置，在同一写事务与锁内取对应作用域 `MAX(sort) + 1`，空列表从 0 开始。分类须分别取 kind / parent 范围，账户使用全部本人账户，商家使用本人全目录。种子初始化按稳定模板顺序分配位置，仅在初始化路径执行；个人目录完成后不补种覆盖排序。商家 Ensure 复用既有同名行时保留其位置，只有实际创建才追加；随券、流水和分期保存新增名称也走同一规则并与原业务事务共同回滚。

分类更新与账户输入在 handler / service 之间保留 `sort` 是否提供的区别（例如 pointer 或 presence flag），省略时保留数据库当前位置，显式 0 仍为合法旧客户端输入。`AccountEditor` 删除数值排序字段及相关默认值 / 提交值；`PersonalLiabilityAccountModal` 不再随资料编辑发送旧 sort。旧显式排序参数仍兼容，前端的新拖动入口使用批量接口。

账户建户幂等摘要在分配末尾位置之前计算，不能把随目录变化得到的 sort 放入请求内容摘要。新请求摘要应编码排序字段是否提供，已有请求查找同时兼容旧版规范化摘要：新旧 SHA-256 都由相同输入明确构造，旧摘要仅用于已有记录匹配，新记录写新摘要。重试先返回已有账户，不重新分配位置；不同业务内容仍返回 409。这样无需改变已有 request 表列宽，也不会因新增字段或默认追加改变旧 key 的正常回放。

选择整数位置而非浮点 / 分数排名：这些管理目录规模小，批量连续整数简单、可验证，也避免重命名后依赖名称排序。保留显式旧参数而非删除 API 字段以维持客户端兼容。

### 4. 通用前端分成排序容器、条目绑定和保存控制

建议新增 `components/sorting/SortableCollection.tsx`、`SortableHandle.tsx`、`hooks/useCatalogOrder.ts` 和 `lib/ordering.ts`。职责是：

- 容器接受稳定 `scopeKey`、完整 ID 顺序、保存回调、disabled / busy 与拖动呈现内容，管理拖动上下文、当前拖动项和取消。
- 条目绑定把 ref、位置和手柄传给页面，页面决定外层是卡片、`li`、手机行或 Table 的 `tr`。不能给 Table 塞入无效 div，也不能为了复用把账户行改造成另一套页面。
- 保存控制保留确认 ID 顺序、拖动预览 ID 顺序、发起时基准、pending、错误与恢复入口；只按 ID 调整最新实体对象，回滚不恢复过期余额或名称对象。用最新数据成员与作用域核对，拖动中成员变化则取消预览并重取。
- 正在保存时禁止同一业务目录继续排序或相冲突的 CRUD。确认完成后重取，再开放下一操作；不新增隐式串行队列。目录后台读取不在 pending 期间替换预览，最终以服务端结果与重取完成收敛。
- mutation 捕获 auth epoch 与 scopeKey，排序请求显式传 `_epoch`，缓存写入 / 错误恢复 / 提示前再次校验；组件卸载或弹窗 generation 改变后只允许有效原目录缓存同步，不回填别的弹窗。禁止自动重试时使用新账号 token 发送旧 payload。

采用 dnd-kit 当前 `@dnd-kit/react` 的 `DragDropProvider`、`useSortable` 和 `handleRef`，需要直接配置传感器时显式声明 `@dnd-kit/dom` 依赖。2026-10-14 注册表查询的 React 包为 0.5.0，peerDependencies 支持 React 18 / 19；实施时固定实际兼容版本并提交 lockfile。页面不直接各自实现传感器。

手柄为按钮，中文 aria-label / 操作播报，鼠标设置小位移门槛，触控使用短按住后激活，键盘提供 Space / Enter 拾起和放下、方向键移动、Escape 取消。手柄可使用局部 `touch-action: none`，非手柄保持正常纵向滚动；不在整行禁用触控。拖动完成抑制同次 click，避免打开管理弹窗。减少动态效果时关闭位置动画，保留即时位置反馈。

长列表使用 `DragOverlay` 或库的 clone 反馈，弹窗排序指示位于当前弹窗上层但受当前交互层控制；自动滚动仅针对有效容器。根分类支持当前响应式网格布局，其他列表以纵向排序为主，不强行压成桌面单列。Escape 拖动时先取消并停止向外关闭弹窗，未拖动时沿用弹窗关闭行为。

依据官方 [React quickstart](https://dndkit.com/react/quickstart/) 的当前包体系、[useSortable](https://dndkit.com/react/hooks/use-sortable/) 的手柄与条目绑定、[Pointer sensor](https://dndkit.com/extend/sensors/pointer-sensor/) 的激活约束。使用库封装而非原生 HTML drag：目标含手机触控、键盘和嵌套滚动；不把已标记 Legacy 的 core / sortable 示例混入新版 React API。

### 5. 分类弹窗与页面交互保持清晰

一级卡片保留大类名称、子分类预览和一级维护操作，名称 / 管理内容区域通过可访问触发器进入 `CategoryChildrenModal`（建议新组件），将原 Tag 的子分类维护放进弹窗行列表。根卡片的拖动手柄、创建、重命名、删除均是独立操作，阻止误打开弹窗；不把多个按钮嵌在一个大按钮内。

弹窗状态只保存 parent ID，数据从最新本人分类树派生，避免缓存整份旧 children。使用 parent ID + kind + auth epoch 构成作用域；内部提供添加子分类、每行改名 / 删除及手柄。空大类也可进入，展示空态和新增入口。拖动自动保存，底部关闭操作只关闭；关闭不取消成功保存，也不补一次批量提交。名称编辑可复用现有表单弹窗逻辑和 viewport keyboard Hook，焦点按当前层返回。

账户手机行与桌面表格复用同一个保存控制，保留编辑、删除、基金持仓及负债详情链接。平台管理在 `search.trim()` 非空时禁用排序并显示“清空搜索后可拖动排序”，清空后使用完整目录。排序未完成时同一目录的编辑 / 删除 / 新增暂时禁用，搜索和关闭操作可用但不会改变在途请求的作用域。

选择弹窗内纵向子分类行而非继续拖动换行 Tag：手机目标更大且动作不会与 Tag 的删除关闭图标混淆；一级卡片保留预览，保持浏览效率。选择搜索时禁排而非把过滤结果合并回完整顺序：行为更容易理解，也不制造隐藏项位置歧义。

### 6. 缓存更新以服务端目录顺序为准

三个 API 模块增加排序 mutation，但不复用 `useInvalidation('category'/'account')` 的全业务失效集合。排序成功只更新 / 重取对应会话的 categories、accounts 或 voucher-platforms 目录；相关选择器本已共享这些 queries，可直接获得新顺序，不需要强制刷新流水、统计、预算或资金历史。

商家 `platformCache.ts` 删除按名称排序，维护 create / rename 响应中的 sort，以 `sort, id` 更新位置或原位合并条目，delete 只移除 ID；保留 cancelQueries 之后再次核对 epoch 的保护。排序响应只包含 IDs，先按当前实体重排，再重取完整目录。非排序 CRUD 保持其既有必要业务缓存失效，不在此改动中缩减资金操作刷新范围。

`accountOptions`、`categoryIndex` 和 `PlatformInput` 目前都保持输入相对顺序，应继续只过滤 / 映射；加入真实过滤场景测试而不是另造名称排序。排序更新不向表单触发主动选择，不清除历史选择或金额草稿。

## Risks / Trade-offs

- [全账本锁会短暂与资金写入串行] → 沿用已存在的一致性边界，只加载目录元数据、批量写位置，不计算账户余额，不增加新财务写入；锁优化留待出现实际性能问题时处理。
- [手机拖动与页面滚动或弹窗关闭冲突] → 专用 44px 手柄、局部触控约束和激活门槛，拖动时拦截 Escape / click；以真实浏览器输入验证滚动与取消。
- [后台重取覆盖预览或失败回滚带回旧财务数据] → 仅管理 ID 顺序，使用最新对象，保存期间保持预览并在结束后重取。
- [两个设备同时编辑目录] → 使用完整 previous_ids 做冲突检查，不静默覆盖；显示最新列表后由用户重新调整。
- [未知网络结果与已提交排序不同] → 本地失败先恢复确认顺序，再重取服务端；重试原请求仅在目标已生效或基准仍匹配时成功。
- [新商家字段和旧客户端 / 旧代码并行] → 数据库先加列，默认值允许旧写；新版后端和前端配套上线。发布期间暂停写入，避免旧 Ensure 在新列回填后继续插入默认 0 扰乱顺序。
- [已有主规范仍有旧“共享平台目录”措辞] → `accounts` 中“消费信用类型目录来源”及“账户创建可靠性”的历史句子与当前个人平台主规范不一致。本方案遵循已完成个人化的归属实现及 `voucher-platform-options`，不扩张为共享目录；相关措辞另行清理，不复制进本次新增要求。

## Migration Plan

1. 后续 apply 开始时复核已有迁移编号并采用下一个空闲编号（当前为 `000016_catalog_ordering`），在 `000015_personal_voucher_platforms` 之后创建 up / down，保留既有迁移。
2. 部署迁移前备份并暂停应用写入与 worker。为 voucher_platforms 增加 `sort NOT NULL DEFAULT 0`，按每个 owner 分组、`BINARY name, id` 的升序分配连续位置，和当前 Go 精确名称比较保持同一初次显示顺序；新增本人顺序索引和排序请求结果表。不改 ID、owner、名称或创建时间，不触碰财务表。
3. 在隔离 MySQL 数据库测试空库 / 已有个人目录升级、含大小写及中文 / Unicode 的名称回填、前后金额与业务文字快照、排序与新建并发、注入中途写失败；SQLite 测试不能替代 MySQL 锁和迁移验证。
4. 先部署支持排序的后端，再部署前端，在暂停写入窗口内完成；验收成功恢复应用写入。服务重启不得重新回填目录顺序。
5. 应用回退可先保留新增列和个人数据，但旧代码将重新按名称显示商家。down 移除排序请求结果表、新增索引及商家 sort 列，不回滚个人归属或名称；执行后商家自定义顺序丢失，须在维护窗口记录并导出其值。分类和账户已有 sort 列不删除，已有财务数据不回退。若继续回退到 `000015` 之前，须另外满足该迁移自身的目录变更回滚 guard，不能用本次 down 绕过它。
