## Context

动机见 `proposal.md`。现有 `voucher_platforms` 仅保存 `id`、精确名称与创建时间，通过全局唯一索引去重，没有创建者或归属；券和流水保存 `platform` 字符串，没有目录外键。目录 GET / POST 只验证登录，`VoucherService.ListPlatforms` / `CreatePlatform` 和仓储 `List` / `Ensure` 均没有账号参数。

目录自动补入存在于券创建、创建幂等重试与修改，以及 `TransactionService.create` / `update`。固定分期新消费通过 `liability_installments.go` 的事务内 `inner.create` 进入流水路径，因此必须复用同一归属写入，不能遗漏内层事务。现有业务资源按资金账户归属，遗留记录的 `created_by` 可能不是现归属账号，不能用它确定目录归属。

分类已有 `category_ownership.go` 和 `catalog_initialization.go` 的全角色本人管理与一次初始化模式；`000012_personal_catalogs` 为已有账号复制旧分类并保存迁移快照。当前最高迁移编号为 000014。平台目录仍在主规范及 README 中明确要求共享，本次需求有意替换该行为，四份 delta 统一变更，不能只改前端入口。

前端 `Mine.tsx` 的“我的记账选项”提供账户 / 分类入口，`App.tsx` 使用登录壳内懒加载路由，`navigation/routes.ts` 显式将个人管理路由归到“我的”。`api/vouchers.ts` 的目录 query / create hook 共用 `voucher-platforms` 会话 epoch key；`PlatformInput` 已有编辑生命周期守卫，`QueryBoundary` 与手机可视区域设施可复用。

## Goals / Non-Goals

**Goals:**

- 用显式账号归属贯穿目录 API、内部业务事务和迁移，数据库保证账号内精确名称唯一，任何无身份业务路径都不能回退全量目录。
- 保留字符串业务接口和历史文字，以独立候选目录满足个人维护，不重算账务或改变金融操作授权。
- 复用现有事务、查询缓存和响应式界面设施，让管理页和字段内创建维护同一份本人数据。

**Non-Goals:**

- 不引入商家画像、商家分类、跨账号共享 / 合并、批量改写历史商家文字或目录排序配置。
- 不为券和流水增加强制平台 ID，不调整资金账户、分类、负债类型、预算或账期的既有归属。
- 本变更的 propose 阶段只生成规划材料；生产迁移和部署由后续实施与发布流程执行。

## Decisions

### 1. 保留目录表和接口，以显式 owner 约束全部目录操作

`VoucherPlatform` 增加非空 `OwnerID`，`voucher_platforms` 增加用户外键，原 `uk_voucher_platform_name` 替换为 `(owner_id, name)` 复合唯一索引，名称保持 `utf8mb4_bin` 精确比较。保留现有表名及 `/voucher-platforms` API，返回的 `id` / `name` 结构不变；业务意义不限于券，无需为改名而迁移所有调用位置。

服务接口接受 actor，仓储 List / Ensure / Update / Delete 接受显式 owner ID；处理器从现有认证上下文传递 actor。查询只能按 owner 取数，创建忽略或拒绝请求中的归属字段。更新 / 删除先读取 ID 并校验归属，存在但属于他人返回 403，不存在返回 404；所有角色都适用，不能复用管理员设置门禁。目录列表不新增按 owner 任意查询的管理接口。

替代方案是只在前端按创建人过滤。旧表没有创建者，而且可绕过界面调用全局接口，故需要服务层与数据库范围共同执行。也不另建同语义“商家”API，以减少旧客户端兼容面。

### 2. 默认模板与一次初始化独立于个人实例

新增数据库 `voucher_platform_templates`，使用精确名称作为稳定模板键，迁移写入既有九个默认名称；新增用户 `voucher_platforms_initialized` 标记。新账号首次读目录、独立创建或随业务保存前，在事务内按既有锁顺序锁定用户行，读取模板、补齐本人缺少的同名项、提交标记。已有同名项复用 ID，不以“目录是否为空”判定是否初始化，允许本人清空所有未使用候选后仍保持已初始化。

模板只保存产品默认名称，不从任何账号当前目录或升级快照派生新账号模板。标记一旦完成，列表读取、启动和模板变化均不补种；只有用户明确创建或业务成功保存能再次添加同名项。事务内 helper 接受已绑定的数据库事务，外层提供初始化入口，不能在券 / 流水 / 分期事务内再开启独立提交或重入账本锁。

替代方案是每次启动补缺失默认名称，会恢复已删除项；将个人目录作为默认模板会传播私有自定义名称，均不采用。

### 3. 旧共享目录一次复制为已有账号的独立副本

旧表未记录创建者，无法可靠判断“只在输入框创建、尚未记账”的名称归谁。采用与旧分类个人化相同的保留策略：迁移冻结整个旧目录，为迁移时已存在的全部账号建立独立副本，保留名称和创建时间；原 ID 归初始管理员（最小管理员 ID，无管理员时最小用户 ID），其他账号分配新 ID，并记录旧 ID / owner / 新 ID 映射。数据库无用户时保留旧快照用于审计，不在运行时提供 owner 为空的公开选项，新建账号按默认模板初始化。

对每个已有账号补齐稳定默认项，再从该账号主要资金账户所属的保留流水及券支付账户所属的保留券中按相同规范化规则补入缺少名称。软删除 / 已撤销但仍保留的历史记录纳入补入与引用判断；采用 `accounts.owner_id` 而不是 `created_by`，不因遗留转账另一端的历史展示开放他人目录。归属缺失或非法历史名称必须在迁移预检报告中指出并使切换停止，不能静默截断或借归属猜测修改历史数据。

迁移完成后为所有已有账号设置初始化标记。目录副本从此不再互相同步，后续新账号仅有稳定默认项。财务表仅只读核对，不更新券 / 流水平台、ID、时间、创建人、请求标识或金额。

替代方案是把整个目录只交给管理员，其他人仅按历史补入；它会丢掉成员明确创建但未使用的名称。按历史使用人分配也不能恢复不存在的创建者，因此保留升级前已公开名称的一次独立副本。此决定仅针对既有账号升级，不能演变为运行时复制私人目录。

### 4. 管理目录与财务字符串快照分开

新增 PUT `/voucher-platforms/:id`，输入 `{ name }`，成功返回原条目 ID 与新名称；本人已有其他同名项返回 409，不合并实体，改回同一条目原名为成功无变更。新增 DELETE `/voucher-platforms/:id`，无引用时删除条目并使用现有空响应约定，已不存在为 404。

重命名仅更新目录行，不修改历史字符串或已打开草稿，管理页提示“仅修改候选名称，历史记录保留原文字”。目录没有外键，删除引用判断按本人资源归属，对 `transactions.platform`、`vouchers.platform` 去除首尾 Unicode 空白后精确匹配当前名称，包括被软删除或撤销但仍保留的记录；他人同名不能阻止本人删除，也不能通过提示暴露他人使用信息。重命名后旧文字仍是历史快照，未来用户明确保存旧名时允许在本人目录重新建立条目。

目录新增 / 更新 / 删除采用现有 `repository.LedgerWrite` 事务守卫，与资金写入统一锁顺序，引用检查与删除原子执行，避免检查期间另一业务写入同名记录。服务内同名并发创建仍以数据库唯一约束和当前已提交读取获得本人同一项；更新重名应明确识别复合唯一冲突，不能吞掉其他存储错误。完整锁序为账本守卫、用户初始化锁、目录行，不嵌套独立 LedgerWrite。

替代方案是引入平台 ID 并重映射所有财务引用，以让历史展示跟随改名；这会改变字符串接口并扩大迁移面。纯粹允许删除使用中候选虽可保留字符串，但用户要求参照分类管理，本次采用保留引用的删除约束。

### 5. 所有隐式补入只写业务资源所属账号，保持原子性

`ensureVoucherPlatform` 和 `TransactionService.ensurePlatform` 增加必需 owner 参数，移除生产无 owner 的回退路径。券创建、既有请求幂等重试与修改均在已有业务事务内补入本人目录；流水创建 / 修改与固定分期 `inner.create` 一致传递认证 actor，经既有资源归属校验后确保 owner 与资金账户相同。对遗留创建人不同但当前资源属于操作者的合法修改，目录归操作者，不能归原创建人。

目录首次初始化及随业务名称补入使用传入事务；业务失败时新名称和财务写入一起回滚，用户先前明确单独创建的条目不受影响。已有后台到期退款无需重建目录；如内部写入路径确实需要补入名称，只能从已保存账户 / 券的 owner 解析，不能使用当前补处理请求的 actor，也不能改动原事件创建人。

替代方案是业务成功后另发目录创建请求。它会出现财务已成功但目录失败的部分状态，也无法与分期内层事务回滚一致，故仍保留事务内补入。

### 6. 复用目录缓存，增加“我的”管理路由与页面

新增懒加载 `pages/Platforms.tsx`，注册登录壳内 `/platforms`，在 `Mine.tsx` 的“我的记账选项”增加入口，并更新 `activeKey` 将此路由归到“我的”。所有角色可达，不增加 `RequireRole` 管理员限制，账号切换复用已有认证清理。

页面采用现有 `page` / `panel` 样式、名称列表和搜索框、明确新建按钮、行内重命名与删除确认。长名称允许换行，窄屏操作换行而不隐藏，删除不依赖 hover；触控热区与明暗主题遵循 ui-shell。新建 / 重命名使用已有 Modal 与可视区域键盘避让，不自动聚焦手机文本框，保存时防重、内联校验 Unicode 字数，失败保留草稿；首次失败、后台更新失败、空目录、搜索无匹配分别展示。

保留 `api/vouchers.ts` 当前目录 query key 和创建 hook，为重命名 / 删除扩展 hooks；成功只取消 / 更新 / 失效发起账号 `voucher-platforms` scope，不无差别刷新财务视图，不复制另一账号缓存。发送请求时捕获 epoch，响应时验证会话仍有效，旧 epoch 响应不得重新填充已清理缓存或在新账号弹成功消息。`PlatformInput` 增加会话有效性校验，保留现有编辑对象 / 字段版本守卫，目录刷新不自动替换表单文本。

替代方案是管理页自建第二套目录缓存，会让业务候选和管理列表不一致；因此共用同一资源 key，并补齐 mutation 对换号的保护。

## Risks / Trade-offs

- [旧共享目录无法还原名称创建者] → 为已有账号保留一次独立副本；新账号仅初始化默认模板，迁移后禁止同步私人修改。
- [全局唯一约束遗留或内部 helper 漏传 owner] → SQL 与模型索引一起替换，搜索并更新全部 Ensure 路径，以跨账号同名和分期回滚测试验证。
- [改名与历史展示的预期不同] → 管理页说明候选 / 历史文字关系；用历史券、流水、封账记录验证不会批量改写。
- [读取初始化或目录写入扩大锁范围] → 完成标记后目录查询直接按 owner 读取，仅未初始化及目录写入进入事务；复用既有锁序并验证并发和失败重试。
- [账号切换后缓存或消息污染] → epoch 校验覆盖读取、mutation 缓存写入、字段回填及成功提示，使用受控迟到响应验收。
- [MySQL DDL 无法整体事务回滚] → 切换前快照和预检、暂停写入，逐步核验；down 在任何目录 / 模板 / 初始化或账号集合发生变化时拒绝自动恢复。

## Migration Plan

1. 先在独立 MySQL 测试库验证。实施时采用下一空闲编号（当前候选 000015），提供完整 up / down，不改已发布迁移。
2. 正式切换前备份，暂停业务写入及后台 worker；快照原目录、用户初始化状态，并读取券 / 流水数量、身份、文字与余额基线。预检账号归属和名称是否合法，问题未解决前不继续切换。
3. 增加 owner、模板、标记及映射，为已有账号复制旧目录 / 补齐默认及本人历史名称，将所有运行目录行落实到非空归属，再替换全局索引。保存迁移后基线用于 down 比较。核验副本身份、精确去重和财务基线不变。
4. 协调切换后端与前端，重建或清理旧目录会话缓存，验证四角色个人管理、越权拒绝、字符串业务保存、手机与桌面导航，确认后台使用持久化归属后恢复写入。
5. down 先对比迁移后的目录、模板、初始化状态和账号集合；只在未发生用户维护、新账号初始化或其他目录改变时，按原快照无损恢复旧目录及索引。已启用后的私人目录不能自动合并成共享表，守卫不满足时返回明确错误，保留当前数据并采用备份或另行设计的数据回退；任何回退不得删除新财务记录或批量改写历史文字。
