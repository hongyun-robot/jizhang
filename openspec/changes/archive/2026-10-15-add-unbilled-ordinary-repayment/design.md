## Context

动机见 `proposal.md`，产品约定见 `specs/liability-billing/spec.md`。本次修改跨越前端预览、服务层写入、持久化分配和历史操作，需要明确设计。

现有实现观察：

- 普通消费支付时，`backend/internal/liability/ledger.go:RecordChange` 已生成真实本金债项与未出账账单，无需提前出账或补造支出。
- `frontend/src/components/LiabilityDialogs.tsx` 的 `payableBills` 和分配预览只包含 `issued_at` 非空账单；服务层 `prepareOrdinaryRepayment`、`TargetsJSON` 和 `Reallocate` 也限制已出账。
- `prepareOrdinaryRepayment` 在账户存在任意分期时进入专门路径，因此不能只修改「没有分期」分支。
- `Reallocate` 会重算历史自动资金。直接去掉出账过滤会改变旧还款范围，也可能使历史资金抵扣后补消费。
- `repository.LedgerWrite` 将财务操作串行化，并在事务最终状态检查所有资金完整分配；`LiabilityService.operation` 提供归属、幂等、前后快照和缓存更新。新功能复用这些边界。
- `LiabilityCreditEvent.Mode` 为长度 32 的字符串，`Targets` 为文本 JSON；现有 SQL 使用 VARCHAR 而非枚举。可以增加持久化模式及明确债项目标，不新增列。
- 当前普通 `Repay` 只解析日期并检查还款账期开放，禁止未来日期及不得早于消费是本次未出账分支新增校验，不能误以为现有入口已覆盖。
- 主规范「实际还款日期必须晚于账单日」位于账单规则配置语境。本次增量将其明确为**约定到期日**限制，避免与实际提前支付冲突。

## Goals / Non-Goals

**Goals:**

- 将范围筛选、金额计算和确定目标封装为一个服务端计算过程，供预览和事务内提交复用，预览不承担写入职责。
- 新还款保存固定消费目标；既有已出账与分期行为保持兼容，所有金额按既有 decimal／分单位口径处理。
- 支持不同生命周期的同账户数据共存：只有普通消费、混有分期、已出账与未出账并存、消费自身账期已封账。

**Non-Goals:**

- 不重写全部历史自动分配，不为旧资金回填新模式或迁移目标。
- 不扩展普通转账、退款或收入的自动偿付范围，不在旧重新分配弹窗增加未出账模式。
- 不引入支付网关、新依赖或新的数据库资金来源。记录完成表示账务登记，非对外实际付款。

## Decisions

### 1. 范围与分配方式分开表达

扩展 `LiabilityRepaymentInput` 和前端 `RepaymentInput`：

| 字段 | 行为 |
| --- | --- |
| `scope` | 可选，`issued` 或 `unbilled_ordinary`；省略和空值按 `issued` 处理，其他值拒绝 |
| `mode` | 保持 `auto`／`manual`，不把还款范围挤入现有分配方式 |
| `targets` | 保持按 `statement_id`、`amount` 输入，仅手动模式允许；客户端不能直接指定内部债项来绕过校验 |
| `quote_signature` | 新范围提交必填，绑定本次计算输入及相关当前欠款状态；已出账旧请求不要求该字段 |

`POST /liabilities/repayments` 按范围分支。`issued` 继续调用现有路径；`unbilled_ordinary` 先进入新计算与固定目标路径，再生成同一类 repayment 操作，不经过分期自动整期推断。未知字段及非法范围须明确报错。

未采用全局放开 `issued_at`：它会改变默认自动还款、旧客户端、通用转账、退款和重新分配的外部行为。用户已明确选择显式切换范围。

### 2. 以真实消费债项筛选普通可还本金

新增针对未出账普通消费的计算模块，读取账户债项、来源流水、账单、现有分配，统一计算合格集合：

- 债项 active、`kind=principal`、`plan_id` 和 `term_id` 均为空，有真实来源流水，且剩余金额为正。
- 来源为当前负债账户实际支付的消费，资金影响为负；普通支出与购券真实支付均可纳入。来源为转出转账、券核销／作废或计划费用时排除，不能仅凭 `term_id` 为空判断。
- 账单属于目标账户、类型为 monthly、当前未出账；消费实际日期不晚于所填还款日期。
- 不按当前自然月或到期月份裁剪；所属账号、可支付现金资产账户及角色按现有规则校验，停用负债沿用既有可还款能力。

按到期日、账单周期结束日、账单 ID、消费日期、来源 ID、债项 ID 排序。自动模式依序消耗普通本金；手动模式先校验无重复账单、金额合计等于还款额、各账单普通容量足够，再按相同账单内部顺序生成逐债项目标。不改变用户未选范围的资金分配，也不要求先还清已出账普通欠款。

日期使用账本时区和服务可注入时钟。只对新增范围要求 `entry_date <= today`，且还款自身账期开放；容量过滤自然排除消费日晚于还款日的目标。原消费封账不触发编辑原消费。

未采用按账单 `remaining` 直接加总：同一账单可能混合普通消费、分期本金和费用，账单总未还额不等于普通可还金额。

### 3. 服务端预览与保存使用同一计算

增加 `POST /liabilities/repayments/preview`，只计算 `unbilled_ordinary`。请求包含目标负债、扣款账户、实际日期、正金额、分配方式及手动目标，不需要写操作请求标识。返回：

- `scope`、`available_amount`、`amount`；
- 合格账单列表及各自普通可还金额、周期、到期日；
- 本次分配行：账单、来源消费、债项标识及金额；
- `quote_signature`。

前端可从已有详情推导初始可还提示，但保存必须使用服务端预览。超额时返回业务冲突及最新可还金额供刷新；空态无需制造零金额预览。

签名采用与分期预览相同的规范化状态摘要方式，覆盖 actor、账号、范围、扣款账户、日期、金额、分配方式、规范化手动目标、合格债项剩余状态、账单状态和计算出的逐项目标。摘要是乐观并发校验值，不是替代权限的授权凭证，不引入新密钥。

提交在 `operation`／`LedgerWrite` 内重新计算与比对：目标发生变化、被退款／还款冲减、转分期、账单出账或影响本次分配的规则变化时返回冲突，要求重新核对。匹配后才写资金和固定目标。不信任客户端分配行或其摘要替代服务端计算。预览不得调用会补出账、建账单、写审计或落地分配的读取辅助函数。

相同请求标识重试优先恢复原成功结果，再考虑当下欠款状态，避免成功后响应丢失时被「余额已变化」错误阻止。保持请求体指纹校验：改范围、金额或目标必须使用新标识。现有 `operation` 按输入结构 JSON 计算摘要，新增字段须追加并使用 `omitempty`，将显式 `issued` 规范化为空值，保持缺省新字段时历史请求的 JSON 字节序及摘要；用升级前结构生成的已成功请求验证升级后可重试。

未采用只在前端过滤：后端必须抵御混合分期目标、跨账户请求和并发写入。

### 4. 新模式固定逐消费目标

新增持久化 credit mode `ordinary_advance`。`targets` 存储服务端计算的 `debt_item_id` 与金额；账单信息通过债项与操作快照追溯，避免合法移账后因旧账单 ID 不匹配而丢失偿付。现有 operation 只保存输入摘要与前后结果，没有请求正文列，因此在 `LiabilityResult` 追加可选的 `repayment_scope`、`allocation_mode` 和本次目标摘要，写入已有 `ResultJSON` 供历史展示，不新增请求快照列。UI 不将新模式显示成「手动指定」或「分期整期分配」。

`Reallocate` 将新模式作为明确固定目标处理，和既有 settlement 一样在自动 FIFO 前保留，但独立识别普通消费语义，不借用分期模式。固定记录之间使用稳定顺序并严格核验目标容量，不裁剪金额后继续，不回退自动分配。提交新还款时只能使用扣除全部既有有效分配后的容量，不能通过优先级抢占旧还款或退款。

重算后及 `ValidateRepaymentWrite` 最终检查：每笔有效固定还款仍与其目标及金额一致，目标 active、来源仍为合法普通消费、日期仍合法，全部资金分配完毕且债项无负剩余。**未出账只在创建时校验**；已成功固定的还款在正常出账后仍有效。合法改还款日及移账不改变其消费 ID。新增或后补消费即便排序靠前，也不重排旧目标。

写入顺序复用统一事务：校验预览 → 创建一笔转账 → 配置对应 credit 固定模式和目标 → 重算分配 → 记录操作结果 → 最终不变量校验。任何中间失败全部回滚；不提前出账、不新建还款对应的消费债项。

未采用只存账单 ID 或保留 auto 模式：它们不能保证后来补记同账单消费或修改到期日时偿付仍指向原消费。未采用新建分期结清单：普通消费可以部分偿还，不需要移动账单或生成分期记录。

### 5. 历史操作以撤销重记维护固定目标

新转账关联 repayment 操作，扩展 `liability_links.go`、普通还款编辑／删除／重新分配检查以及历史按钮条件，识别 `ordinary_advance` 后引导至已有 `Reverse`。不允许通用流水修改或旧分配接口将固定记录转回 auto。

撤销复用普通 repayment 分支，只失效本笔 credit／allocation 并移除对应转账资金影响。原消费和其历史账单保持，已出账时恢复真实应还。权限、本人资金来源、还款自身封账及后继依赖检查继续生效；相同撤销请求可重试。旧已出账还款编辑与分期期次撤销流程不变。

修改消费使金额低于已固定偿付、改消费日到还款之后、删除／转分期使目标失效时，最终检查拒绝整个写入。退款先在既有规则允许的剩余真实欠款内分配，不能挪走固定还款以腾出原消费退款空间；资金没有足额合法目标时整体拒绝，真实到账资产时按资产退款原有规则登记。

未采用新增通用的固定提前还款编辑器：现有撤销记录能提供明确审计与资金恢复，本次不扩大产品入口。

### 6. 弹窗复用、预览失效及历史文案

修改 `RepaymentFields`、`LiabilityDialogs`、`features/liabilities/input.ts`、API 类型及客户端：

- 在还款弹窗展示范围选择；默认「还已出账」。未出账范围自动分配文案为「按到期日分配未出账消费」，手动选择仅展示普通可还金额为正的未出账账单。
- 切换范围清空旧目标、旧预览及失效金额，保留扣款账户和实际日期；可还金额只展示选中范围。存在已出账／逾期未还时明确本次不包含这些欠款，不阻止显式选择未出账。
- 新范围增加「核对还款金额」，未完成有效预览时禁用保存。变更所有影响计算的字段时清除预览；忽略较早发出、较晚返回的响应，服务端冲突保留草稿并要求重新核对。
- 沿用 `submissionGate` 和请求指纹：相同内容失败重试保持请求标识，内容改变生成新标识，防止双击与响应丢失产生重复流水。
- 历史明确标识「未出账普通消费提前还款」并可查看消费来源及撤销入口。只读用户维持查看权限；不展示不可执行的写按钮。
- 使用现有选择器和弹窗滚动组件，验收 474×884、390px 手机及桌面尺寸，确保日期、目标、预览和底部按钮可达。

## Risks / Trade-offs

- [共享分配器扩大旧资金范围] → 默认分支和旧模式保留 `issued_at` 限制；新范围仅接受显式请求，补充通用转账、退款、收入和重新分配回归。
- [部分提前还款之后退款或转分期受限] → 固定目标保证资金追溯，发生冲突时明确关联还款及撤销路径，不静默挪款。
- [新模式被旧后端当成 auto 重算] → 发布及回滚必须识别数据语义变化；不能因没有 DDL 就把旧程序直接接到已有新模式记录的库。
- [预览与自动出账竞态] → 提交在现有资金锁内重新计算；出账状态变化返回冲突。预览只读不锁住用户操作时间。
- [前端初始提示与后端候选有差异] → 两端都覆盖日期与混合分期场景，确认以服务端预览为准，提交永远重新校验。
- [固定目标处理影响历史记录] → 仅新模式固定目标，历史 auto／manual／settlement 不做批量重写；核对新增还款与历史资金并存下的金额及分配。

## Migration Plan

1. 无计划新增表或列，保留现有 SQL 与全部历史金额；实施时确认 mode 长度及 JSON 可容纳新值，独立 MySQL 测试验证持久化和重启后重算。
2. 部署前备份，短暂停止财务写入，按现有规则核验无未分配资金。后端与前端作为同一发布单元更新，更新后再开放写入，避免旧后端忽略新范围字段。此计划不授权在规划阶段部署。
3. 发布后在临时账本验证 1000 元普通欠款提前还 300 元，资产减少 300 元、负债减少 300 元、未还 700 元，随后正常出账和撤销均可核对；生产仅执行只读核对。
4. 若尚无 `ordinary_advance` 记录，可恢复旧应用。若已有记录，回退界面仍须保留能识别固定目标的后端；回退后端必须使用带兼容补丁的版本，或先暂停写入并核对、按真实情况逐笔处理记录。禁止直接把 mode 改为 auto、清空目标或自动撤销真实资金；从备份恢复须另行评估备份后的全部财务写入。
