## Context

动机及已确认产品规则见 [proposal.md](proposal.md)，验收契约见 [认证增量规范](specs/identity/user-auth/spec.md)。本设计涉及前后端会话状态、即时撤销和不兼容切换，需随提案提供。

已检查的实现约束：

- `backend/internal/service/auth_service.go` 每次登录追加独立 refresh，没有类型或稳定 session ID；JWT 只有 UID、角色、用户级 epoch。`Refresh` 以分离的 GET/DEL/SET 轮换，任何读取错误都会尝试根据未验证的 UID 前缀执行 `RevokeAll`。
- `auth_handler.go` 的 `jz_rt` 为 HttpOnly、SameSite=Strict Cookie；路径来自配置，需兼容 `/api/v1/auth` 和子路径部署。access 仅保存在前端内存。默认有效期是 30 分钟及滑动 720 小时。
- `Authenticate` 已逐请求查用户，epoch 的 Redis 读取错误目前会放行；`Logout` 目前只删一个 refresh。`user_service.go` 的角色、状态和密码操作都会调用账号级撤销，但 `SessionRevoker` 当前不返回错误。
- `frontend/src/auth/coordinator.ts` 有单页刷新去重和本地 epoch 防迟到结果；不同标签页没有协调。`api/client.ts` 对所有 401 都尝试刷新，`RequireAuth.tsx` 恢复失败只保留登录回跳，没有失效原因。
- 历史 `2026-10-02-add-ledger-system/design.md` 和 `TestRefreshRotation` 明确将旧 refresh 重放视为全账号撤销。本次有意替换该设计：未知或旧凭据不能授权任何撤销；管理员安全操作及用户明确退出才触发账号级撤销。
- 浏览器测试使用真实 AuthService 与临时 miniredis。`frontend/e2e/support/fixture.mjs` 的 `fixtureApi` 会额外登录；新规则下会与电脑页面互相替换，必须一起调整。

## Goals / Non-Goals

**Goals:**

- 以独立会话身份和服务端原子提交为认证边界，不依赖页面清状态实现撤销。
- 将同类替换、当前客户端被动结束、账号级撤销分为不同操作，防止旧客户端扩大退出范围。
- 保留单页重试、资金操作标识、晚到响应和换号隔离，并扩展到共享 Cookie 的标签页。
- 沿用 MySQL 用户表、现有 Redis 和现有认证路由，不增加基础设施或运行时依赖。

**Non-Goals:**

- 不增加 Redis 与财务数据库之间的跨库事务，不撤回撤销前已经通过认证的资金操作。
- 不缓存可继续放行的会话有效性，不承诺浏览器上报信息对应真实硬件，不增加硬件指纹。
- 不增加独立设备管理界面、单设备退出 API、WebSocket 或跨设备退出轮询。

## Decisions

### 1. 设备类型由服务端归一化，建立后不随页面变化

登录请求可附加经过长度、类型及范围校验的浏览器能力信息，例如 `max_touch_points`；User-Agent 取自请求头。服务端用一个集中、可表格测试的分类器得到 `phone | tablet | desktop`，不接受调用方任意指定最终类型。

分类优先识别明确的 iPad/平板标识、Android 非 Mobile，以及 Macintosh UA 配合多触点信息的常见 iPadOS 情形，再识别 iPhone/iPod、Android Mobile 等手机；其余归电脑。Macintosh 的触控推断是启发式，不扩展到 Windows 触屏电脑。禁止按窗口宽度、横竖屏、缩放或后续刷新重新分类。浏览器配置/无痕窗口各自登录占用该类型名额；同 Cookie 存储空间的标签页不占额外名额。

iPad 可以发送与 macOS 相同的 UA，单靠服务端 UA 无法可靠区分，这是接受浏览器能力补充和允许误判的依据；此信息不参与权限授权。[WebKit 官方说明](https://webkit.org/blog/9674/new-webkit-features-in-safari-13/)

备选：用户手选类型会增加登录操作且更容易误选；硬件绑定超出浏览器可可靠提供的能力和本次范围。自动识别并保留明确兜底符合已确认规则。

### 2. 每账号一个有界 Redis 状态，最多三个活动槽位

新增独立键空间，采用一个用户级 Hash，例如 `auth:v2:<uid>`。内部封装在认证会话存储模块，不让 handler 拼接键或直接操作 Redis。

| 字段 | 内容与约束 |
| --- | --- |
| `epoch` | 用户级撤销代次，不设 TTL；不存在时仅允许经过完整凭据校验的登录初始化 |
| `phone` / `tablet` / `desktop` | 一个完整会话记录，包含随机 `sid`、epoch、当前 refresh 摘要、创建时间、刷新时间、`expires_at` |
| 槽位内的短期轮换记录 | 仅保留上一 refresh 摘要及短期冲突识别截止时间，不保存旧 refresh 原文，不授予旧凭据刷新权 |

每个槽位最多一个记录，最多三个有效会话；有效期在记录中判断，而非为整个用户 Hash 设置滑动 TTL。过期槽位在下次读取/写入时忽略或清理，不影响其他槽位；不需要无界 token 集合、枚举所有会话或额外清理任务。短期轮换记录限定为上一代，冲突识别窗口使用服务端常量，例如 60 秒，并且不得超过原凭据到期时间。

新版 access JWT 带显式机制版本、`uid`、`sid`、设备类型、epoch、签发/到期时间。refresh 为高熵随机凭据，可带版本、账号、类型和 sid 作为定位信息；服务端必须比较完整凭据摘要才能确认持有权。前缀、sid 和类型本身均不能授权刷新或退出。随机数失败必须返回错误，不能忽略；Cookie 安全属性、配置有效期和内存 access 策略保持不变。

备选：继续按用户保存任意 refresh 集合无法表达稳定会话身份；每设备一份独立 epoch 仍需稳定 ID 与原子轮换。三个固定槽位使全设备撤销和上限成为常数规模操作，也避免在脚本中扫描或推导任意 Redis 键。

### 3. 登录、刷新、撤销均由短 Lua 脚本提交

使用现有 go-redis 的脚本执行能力，不引入新组件。Redis 脚本保证执行期间不与其他命令交错；脚本应保持常数规模，所有参数、数据类型和可预见错误在首个写命令前检查，不能把脚本原子执行误认为异常后的自动回滚。[Redis 脚本文档](https://redis.io/docs/latest/develop/programmability/eval-intro/)

- **登录**：定位候选账号后读取 epoch，再重新读取用于验证的用户快照，校验数据库凭据与启用状态，预先生成 sid、refresh 和候选 JWT；原子脚本核对捕获的 epoch 后写入对应槽位。新槽位提交就是旧会话失效的边界。epoch 已变化则放弃候选并重新校验凭据或返回可重试错误，不直接用旧用户快照领取新代次。JWT/随机数/Redis 提交前失败不替换旧槽位；提交后响应丢失属于已提交但未被客户端确认的登录，客户端可重新登录恢复。
- **刷新**：核对槽位 sid、epoch、到期时间及当前凭据摘要，预备签发后原子比较并替换摘要、延长该槽位有效期，sid 和类型不变。一个旧值最多有一个成功后继；账号级撤销或同类替换先提交时，刷新不能重建槽位。
- **被替换识别**：合法 JWT 的 sid 与该类型当前 sid 不同即为终止会话；没有槽位或已过期同样终止。用户代次不同表示账号级撤销。错误结果不递增代次、不删除现有槽位。
- **全设备退出**：在同一个脚本内验证发起会话仍匹配当前槽位及代次，再递增 epoch 并删除三个槽位。验证和撤销不能分成先查后改，避免旧设备在新登录后发出迟到退出。
- **管理员安全撤销**：可信的用户管理服务调用账号级撤销脚本，不要求目标用户在线；递增 epoch 并清三个槽位。`SessionRevoker` 返回错误，调用方不能静默宣称撤销成功。数据库已更新而撤销失败时返回明确的可重试失败；重试同一角色/状态操作也必须再次撤销，不能以“值未变化”跳过。Redis 不可用期间认证拒绝执行；不引入跨库事务或声称部分失败已经完成。

时间来源通过认证存储边界统一，测试可推进时间；不能让自然过期测试依赖真实等待 30 天。并发顺序以脚本提交为准：同类并发登录最后提交者有效；退出之前捕获旧 epoch 的登录/刷新不能在退出后恢复旧会话；退出之后重新校验成功的新登录不属于“此前会话”。

备选：Go 进程锁不覆盖多实例，分离 GET/DEL/SET 有重复签发窗口；增加一套分布式锁比对一个用户 Hash 执行原子状态变更更复杂。

### 4. 逐请求验证会话，并保留可刷新与终止原因

认证中间件先验证 JWT 的版本、签名、算法、发行者及有效期，再查询服务端槽位和用户启用状态。只有会话仍有效但 access 到期时才返回“可刷新过期”；验证已过期 JWT 的签名后仍可查明被替换/撤销，不能把终止会话统一伪装成可刷新。不使用跨请求的正向有效性缓存。

响应沿用现有 envelope，新增明确的业务错误常量，由 `api/errors.ts` 归一化：

| 结果 | HTTP | 客户端动作 |
| --- | --- | --- |
| access 到期且会话有效 | 401 | 协调刷新，原业务请求最多重试一次 |
| 会话被替换、已撤销、到期或凭据无效 | 401 | 仅结束对应本地会话，保存有限的失效原因，不调用 logout |
| 旧 refresh 为短期内已消费的上一代 | 409 | 有界协调并使用胜出结果，不领取新凭据，不终止有效会话 |
| Redis 或必要的用户查询暂不可用 | 503 | 不放行、不改撤销状态、不清 Cookie，保留重试入口 |
| 已认证但无业务权限 | 403 | 不刷新、不退出 |

`/auth/refresh` 的任何失败响应均不得发送删除 Cookie 的 Set-Cookie，防止迟到失败覆盖新 Cookie；明确无效凭据由客户端结束其对应状态。旧值绝不返回新 token，409 只识别竞争，不是刷新宽限期。60 秒之外的重放仍拒绝且不改现有槽位。

### 5. 多标签页共享生命周期，网络响应须受代次约束

在现有 `createSession` 外增加浏览器协调适配层，继续保持可注入传输和纯时序测试。所有 login/refresh/logout 网络变更优先通过同源、应用 basename 隔离的 Web Lock 串行化，获得锁后重新读取共享生命周期标记，避免等待期间已经退出或换号。锁覆盖整个网络响应处理周期，不能只锁请求发送或 JS 状态写入；浏览器会在 JS 检查代次前应用 Set-Cookie，迟到成功响应也必须被串行顺序约束。

使用 BroadcastChannel 在内存中交换同一 sid 的刷新结果、登录成功和结束事件；access token 不写 localStorage/sessionStorage/IndexedDB，refresh 始终只在 HttpOnly Cookie。可持久化的共享标记仅含非秘密的 sid、客户端代次、事件 ID、退出待确认状态；事件按预期 sid/代次判断，旧事件不能清理新账号。新标签页恢复登录使用现有 Cookie，而非重新提交密码建立另一会话。

令牌响应包含与 JWT 一致的绝对 `expires_at`（Unix 秒）。页面、共享代理及会话协调器均据此判断缓存是否过期；广播和迟到响应不能用最初的 `expires_in` 从接收时重新起算。即使另一个较新本地 token 已经存在，若它也已过期，迟到 401 仍须实际刷新。

Web Locks 提供同源标签页互斥且要求安全上下文；BroadcastChannel 用于同源浏览上下文通信。[Web Locks 文档](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)、[BroadcastChannel 文档](https://developer.mozilla.org/en-US/docs/Web/API/BroadcastChannel)

Web Locks 不可用时，由同源同名 SharedWorker 作为唯一认证网络代理，所有标签页把认证写请求交给同一个内存队列，代理负责带凭据 fetch 并按完整响应结算后执行下一项；不能只在 worker 分配号段后让页面自行并发发送。SharedWorker 可在多个同源浏览上下文共享，worker 内可发网络请求，这里用它承载串行队列而非假设广播能互斥。[SharedWorker 文档](https://developer.mozilla.org/en-US/docs/Web/API/SharedWorker)、[Worker 网络能力](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)

各标签页必须采用同一协调模式；模式切换、worker 故障或请求是否结算不确定时暂停队列，不允许并行启用另一传输。两种能力均不可用或初始化失败时，暂停认证写入，提示使用受支持的浏览器或安全地址后重试；禁止以 localStorage 租约、单页刷新锁或未验证的“只有一个标签页”判断绕过串行保证。需要验收 Web Locks、SharedWorker 代理及两者均不可用的明确错误路径。

服务端仍对重复凭据返回 409 且不清 Cookie。客户端等待可取得的胜出消息；无法取得时在串行队列内最多做一次恢复性刷新，仍冲突则保留显式重试状态，不清有效会话、不循环。缺少 BroadcastChannel 时优先经 worker 端口、否则经 storage 事件传播非秘密的生命周期变更；不通过持久存储传递 token。

实现中 SharedWorker 同时在内存缓存未过期的最新结果，按期望 sid 和被拒 token 合并重复恢复请求；缺少 BroadcastChannel 但 SharedWorker 可用时统一采用该代理。storage 事件只传生命周期标记，新标签页通过代理取得有效结果，不把 token 写入持久存储。

保留并扩展当前 epoch 守卫：对读取、刷新、登录、logout 回执及广播结果核对发起时的 sid 与代次。新版登录要求显式认证协议版本；旧页面缺少该版本的登录请求应提示刷新页面，不建立会话或写 Cookie，避免新旧协调代码混跑。`/auth/refresh` 和 logout 请求携带期望 sid；已有页的期望 sid 与 Cookie 中的 sid 不符时拒绝且不修改 Cookie，防止旧页借新账号 Cookie 操作新会话。首次恢复没有内存 sid 时才允许根据受验证 Cookie 建立状态。新登录广播使其他标签页结束旧客户端代次并同步当前共享身份，不恢复旧草稿。

备选：只解决服务端撤销会留下多标签页轮换竞争；把 token 持久化虽容易同步，却改变既有认证边界；只增加广播缺少互斥与服务端冲突处理，不能保证启动竞争安全。

### 6. 主动全设备退出与被动结束使用不同入口

保留 `session.end(reason, expectedSession)` 为纯客户端清理；只有用户明确点击“退出所有设备”调用网络 logout。`api/client.ts`、守卫、前台校验和被替换广播禁止通过 logout 清状态，避免手机被挤下线后又踢掉新手机和其他类型。

主动退出先捕获 sid/有效 access，持久记录不含凭据的待退出标记，并通知本浏览器标签页停止刷新、清理个人缓存及草稿；随后在协调边界内提交 logout。后端以当前有效 refresh，或仍有效且匹配期望 sid 的 Bearer 凭据验证发起者；Cookie/Bearer 身份冲突直接拒绝。只有原子撤销成功才返回成功并删除 Cookie；无效/旧凭据不删除可能已属于新会话的 Cookie，不做全设备撤销。

网络失败仍保持本地退出和待确认标记，刷新页面也不自动恢复旧 Cookie；展示“当前浏览器已退出，尚未确认其他设备退出”与重试。确认撤销、确认原会话已终止或用户明确重新登录成功后按代次清理标记；不持久保存 Bearer。确认原会话终止只允许结束本地恢复阻止，不代表其他设备已被撤销。错误不能被包装成“所有设备已退出”。

在“我的”修改按钮文案，在登录页区分同类设备登录、账号会话结束和普通过期提示，保留完整站内回跳及权限检查。`visibilitychange` 回到前台及窗口重新聚焦合并一次会话校验，先校验再允许新业务请求；503/网络失败保留可重试状态，终止认证失败清理缓存。其他设备无需实时通知，闲置页面可在下一次请求前继续显示旧内容。

### 7. 测试辅助必须共享预期会话

`fixtureApi` 不再在页面登录后悄悄为同账号创建第二个电脑会话。盘点所有直接 `/auth/login` 以及持有旧 token 的准备、断言和 cleanup，包括 `refactor_foundations.mjs` 中绕过 helper 的直接登录。页面交互后的请求通过页面当前会话获取能力；准备阶段的独立 API 登录必须在 UI 登录前完成，该旧 token 不能再用于后续断言或延后 cleanup。浏览器上下文隔离代表不同设备，User-Agent 与触控信息代表设备分组，不伪造第四种特权类型绕过规则。

保留 `assertFixture` 的回环地址与测试身份检查，使用临时 SQLite/miniredis 账本，不在真实财务数据上验收。`users.mjs` 当前默认开发服务且没有 assertFixture，须先迁移为隔离验收或增加等价隔离脚本才能运行；同时更新 `refactor_navigation.mjs` 等脚本硬编码的“退出登录”选择器。增加多设备脚本并回归用户管理、认证重试、缓存/草稿隔离和资金幂等场景。脚本并发结果至少用本机真实 Redis 复核，避免仅凭 miniredis 判断 Lua 兼容性。

## Risks / Trade-offs

- [设备类型误判或伪造] → 分类器集中、覆盖常见 iPadOS/Android/桌面和未知情况，不以设备类型授权；接受用户已确认的浏览器信息限制。
- [逐请求依赖 Redis 降低故障时可用性] → 短常数规模操作及超时；故障返回 503，恢复后可重试，不通过放行绕过撤销。
- [刷新响应丢失或 Cookie 迟到] → 原子轮换、跨标签页串行化、失败不删 Cookie、有限冲突恢复；无法恢复时明确重试或重新登录，不能复活旧令牌。
- [浏览器协调能力不可用] → Web Locks 与 SharedWorker 代理均不可用时暂停认证写入，说明恢复方式；不以可能覆盖新 Cookie 的并发请求降级，验证两种能力路径和故障恢复。
- [管理员数据库更新与 Redis 撤销部分失败] → 不隐藏错误，重复安全操作仍执行撤销；只有撤销确认后报告完成，不扩展为跨库事务。
- [全设备退出影响其他设备未提交内容] → 入口明确，其他设备在被动结束时按既有规则清理个人业务状态，不自动发全设备退出请求。
- [浏览器验收辅助会话互相替换] → 重构共享 helper，审查使用者，不通过放宽生产会话规则修补测试。
- [撤销前已授权请求仍可能完成] → 保留财务事务和操作键幂等；“立即”以撤销提交后开始的认证为边界，不承诺撤回已开始的记账。

## Migration Plan

1. 实施并完成隔离测试后，同步发布前后端；停止旧后端实例，不混跑新旧认证写路径。保留现有 Cookie 属性和子路径配置，继续启动本机 MySQL/Redis 做开发验证。
2. 新后端强制验证新版机制标记及 sid，不接受旧 JWT 或旧格式 refresh，旧请求直接失败且不进入旧 UID 前缀撤销逻辑。使用新键空间；本次不执行 MySQL 财务结构迁移。
3. 发布时轮换 JWT 签名密钥。当前 Redis 使用 DB 0，旧 `refresh:*`、`refresh_user:*`、`session_epoch:*` 没有应用专属前缀；仅在确认实例或逻辑库为本应用专用后，才清理前两类旧登录数据并保留 epoch。无法证明专用时不按通用通配符删除，保留旧 refresh 自然到期，新版格式和密钥负责拒绝旧凭据。禁止清空整个 Redis或触及其他应用/财务缓存，具体操作留在实施后的部署步骤中执行。
4. 用户统一重新登录一次；验证手机/平板/电脑共存、同类替换、退出全部设备、旧 refresh 不影响新会话、子路径 Cookie 及前台恢复。
5. 若需回滚，前后端成对回退，停止新版认证写路径，清理可证明属于该应用的新版会话状态并再次轮换签名密钥。旧服务无法凭密钥轮换拒绝随机旧 refresh，故回滚前必须先确认旧 refresh 可安全定向清理；若不能证明其归属，则暂停回退旧认证服务并采用向前修复，不能把旧 refresh 带回认证路径。回滚同样要求重新登录，不回填失效令牌、不回滚财务数据，并记录恢复的旧认证行为局限。
