## Context

动机见 `proposal.md`。当前实现已经具备整笔 `settle`、费用按期关联、`LedgerWrite` 总账事务锁、幂等操作记录和专门撤销；本次扩展这些结构，统一改变资金分配策略。

- `backend/internal/service/liability_settlement.go` 的 `previewFrom` 汇总真实剩余本金及已发生未付费用，未来费用进入 `cancelled_fees`；`Settle` 使用已有待抵扣资金、生成独立结清费、取消未来费用并整计划结清。该规则与确认需求冲突，必须替换。
- `backend/internal/liability/view.go` 的 `term.remaining` 只代表本金；真实未付费用来自关联债务明细。资产已支付费用不会形成该负债欠款，不能直接按原 `principal + fee_amount` 收款。
- `liability_installments.go` 的 `postFee` 固定使用计划收取日和费用账户，并通过 `fee_txn_id` 保证一次入账；需要共享校验而允许提前偿付提供实际日期和本次费用承接账户。
- `ledger.go` 的 `Reallocate` 重算全部有效分配，`settlement` 的逐明细固定目标先于自动分配，普通模式只能偿付已出账分期。`TransactionRepo.Create` 会调用 `RecordChange` 并重分配，因此复合操作中间状态不是最终结果。
- `operation` 保存整账户前快照，但普通还款不会增加计划版本。现 `Reverse` 对结清硬校验操作结果版本，撤销又增加版本，无法直接支持多次按期操作逆序撤销；普通还款撤销还需补齐后继资金依赖保护。
- 负债收入、独立退款、周期及券事件、债务修改删除都可能产生余款；只限制分期界面或 `Repay` 无法移除整个模块的待抵扣功能。

## Goals / Non-Goals

**Goals:**

- 在服务层形成统一的期次报价、整期偿付及最终资金分配校验，普通入口不能绕过。
- 复用期次、债务、资金事件、分配和操作快照，在一次总账事务中收费用、偿债、变更状态并验证不变量。
- 把公开的资金暂存能力移除，同时保留原始资金来源和有效历史作为账务审计基础。
- 支持重复请求、并发报价冲突和有依赖的逆序撤销，任何失败保持完整原状态。

**Non-Goals:**

- 不实现任意金额提前偿还、跳期、独立手续费还款、利率推算或额外结清费输入。
- 不因移除待抵扣自动改写旧转账金额、删除历史资金、虚构银行退款，或自动重建历史分期。
- 不把真实退款归入还款约束；不重排本金尾差；不取消尚有效的未来手续费；不改造基金账户模块。
- 不把补记日期实现成账户历史快照回放。报价基于当前真实未还状态，实际日期用于本次流水归期与封账；已有流水金额和实际费用日期保持历史。

## Decisions

### 1. 以连续期次范围作为偿付目标

增加统一服务层输入：`plan_id`、`term_ids` 或 `all_remaining`、`from_account_id`、`entry_date`、`request_key`、计划 `version` 及 `quote_signature`。两种选择形式互斥；后端将期次按编号规范化，拒绝重复 ID、跨计划、已结清目标、跳过最早未还期和中间空洞。前端只需选择“还到第几期”或“全部还完”，默认最早一期，不提供每期金额输入。

建议增加 `POST /installment-plans/:id/repayment-preview`、`POST /installment-plans/:id/repay`，原结清入口作为同一算法的 `all_remaining` 模式。旧的手填 `fee_amount`、费用账户和待抵扣结清请求必须明确返回业务冲突，不能悄悄按新金额扣款；已完成旧幂等请求可读回原结果，新请求走新语义。

替代方案是按账单而不是期次选择。账单可含其他消费、多个计划及已发生费用，无法保证连续整期，也会被普通 FIFO 抢占，因此不用账单作为提前偿付的唯一目标。

### 2. 用真实剩余金额计算报价，保留费用状态维度

每个所选期次计算：

```text
P = 该期有效本金明细真实 remaining
F_posted = 该期有效负债费用明细真实 remaining
F_scheduled = 尚无有效 fee_txn_id、未取消的有效计划费用
term_due = P + F_posted + F_scheduled
total_due = 所选期次 term_due 的合计
transfer_amount = total_due
```

已从资产支付的费用不进入 `F_posted`，已经退款冲减的费用用实际净剩余量，零费用不建流水。一次性费用只属于原配置期次，不能重新分摊。系统用 decimal/分整数运算；前端沿用 `lib/money` 的分精度。

报价返回规范化期次、每期剩余本金、已发生未付手续费、尚未入账手续费及合计、计划版本和签名。已出账与费用已入账是两个不同维度，UI 不把未出账误作没有手续费，不把报价总额写回当前欠款。签名覆盖目标范围、真实债务及分配余额、费用状态/金额/来源、还款账户和日期；提交在锁内重算并逐项对照，不仅对照计划版本。

预览只读。已经到期但未成功入账、封账阻塞、退款待核对、费用配置失效先按现有核对机制处理；还款不能通过改日期避开。用户确认没有本金归零仅剩手续费的历史，本次不提供该例外；若检测到，返回核对原因。日期默认账本今天，拒绝未来或早于原消费日期，实际流水账期必须开放。

替代方案是直接取各期原计划金额，或继续把未来费用累计成任意结清费。前者重复收已付或已退款部分，后者失去期次关联和撤销依据，因此使用逐期真实报价。

### 3. 新费用先计入负债，再通过单笔完整转账一起偿付

尚未入账的所选费用按本次实际日期逐期生成独立费用支出，使用计划支出分类，费用先由当前负债账户承接，形成绑定 `plan_id`、`term_id` 的费用债务，再与本金一起用所选资产账户的完整转账偿清。原计划配置费用账户为其他资产时，本次仍使用这一完整转账；保留未选期次的费用账户设置。

例如本金 1000、手续费 20：生成负债费用支出 20 和资产到负债转账 1020，资产只减 1020，负债费用只计支出一次，最终该期本金及费用都为零。不能在资产直接再扣 20 的同时转账 1020。

抽取 `postFee` 的共享费用校验与创建逻辑，常规到期入账仍使用计划配置，提前入账传实际日期和本次承接账户。保留原计划 `FeeDate` 与配置；实际收取日来自有效费用流水，详情同时可解释计划日与实际日，费用关联使 scheduler 跳过重复收费。提前费用带期次与操作关联，操作者和计划原创建人都可追溯；不把提前费用伪装成无来源的普通手工支出。

操作在 `LedgerWrite` 锁中确定操作前真实报价，创建费用后不得采用中间重分配结果重新减掉本次应付。使用操作前未还本金、既有未付费用和新费用 ID 建立固定逐明细 targets，创建精确 `total_due` 的一笔转账；不读取或借用旧未分配资金。最终重分配并验证全部所选目标为零、新资金全部用完、全账户无未分配余额、实际账户余额满足不变量。

替代方案是费用从资产直接支付、本金另转账，虽能做净额，但容易出现两个付款来源、费用统计和双扣混淆；采用统一负债费用加完整偿付，沿用现有债务和还款历史展示。

### 4. 统一策略覆盖普通还款、重新分配与所有资金写入口

期次偿付约束属于服务层策略。普通还款的自动候选按原到期排序，普通欠款可部分偿付；遇到分期时以整期为不可拆单元，须包含对应尚未发生费用并调用同一费用入账逻辑。手动账单分配也按其涉及的期次核验，不允许指定费用子项单独偿还。无法无歧义匹配连续整期和精确总额的请求整体拒绝并引导至分期入口，不能只跳过不合格期次后形成余款。

同一策略用于分配调整与普通转账。收入等非退款资金事件若实际用于偿付分期期次，也必须通过整期策略，不能只凭资金已用完就留下本金归零但费用未付的期次；无法完整匹配时拒绝并引导核对实际资金用途。普通入口成功完成的分期期次同样标记已还、绑定操作和保护组合流水；全剩余期次结清才令计划 `settled`，部分期数完成时计划保持有效。退款事件标识单独处理，真实部分本金退款继续冲减并产生 `needs_reconcile`，不要求退款凑成整期。

把“所有有效资金 remaining 为零”的约束纳入统一最终检查，覆盖 `Repay`、`Allocate`、`Settle`、普通交易服务和仓储统一写事务、周期与券资金事件。底层 `RecordChange` 仍可建立债务/credit 来源并执行中间投影，复合操作最终统一验证；不可在创建首笔费用或转账的中间点就提交或检查完整组合。单笔普通操作在其外层事务退出前验证，失败回滚所有源流水、余额和分配。重新分配不能使原已全额期次变为部分偿付。

资金事件和 `remaining` 保留为内部分配/审计结构，不再作为待抵扣产品能力；新查询移除 `pending_credit`、`surplus`，新写契约不接受 `hold`。不删除历史 mode/targets 列或旧快照，历史读取仍能解释原记录；不把剩余余额简单改名继续使用。移除原逻辑中“旧余款用于后来消费/账单”的新行为，已完整分配旧资金的固定历史目标保留。

替代方案是只隐藏字段或在 `Repay` 检查金额。普通转入、收入、退款和已付债务删除仍能留下资金，且有账户负余额但存在未分配金额的情况，因此选择最终全账户检查。

### 5. 退款保留真实到账语义，超额原子拒绝

关联本金退款优先冲减原消费，剩余部分按合法欠款目标分配，全部用完才提交。无关联退款和收入执行相同的完整资金分配规则。普通退款超过原消费金额仍只做确认；若目的为受管理负债账户，还必须独立满足完整分配约束。退款到本人资产账户仍按真实到账记录，不自动减少原负债。

没有足额合法欠款的负债退款整体拒绝，表单提示核对实际到账账户；不自动拆退款、不虚构转回资产。券自动退款等固定资金去向事件遇到该限制时回滚其账务操作并保留失败原因，供人工按真实事件处理；不能未经依据改资金目的地。

已有已还消费的降低金额/删除，可能使原还款失去目标，统一检查必须拒绝；可合法删除的普通非分期还款仍恢复欠款。计划管理消费及费用继续由专门核对或撤销处理。

### 6. 保存实际变更与依赖，支持连续逆序撤销

新增按期操作种类及 JSON 结果中的目标期次、有效费用流水、偿付 targets、受影响历史 credit 的前后签名及期次后状态。复用 `BeforeJSON`，但撤销只恢复本次实际影响的期次、费用关联、状态、归属和来源模式，不能把整账户快照覆盖回去。

未出账的已偿付所选明细可沿用按操作创建的 `settlement` 账单，保留原期次计划账单字段及操作前归属快照；未选期次不移动，已出账快照不改写。移动已偿付明细前固定受影响旧还款的真实分配，避免新到期排序改变它；任何被固定来源校验权限和封账。

逆序撤销以最近有效操作及真实依赖为依据，版本持续单调递增用于并发，不拿旧结果版本硬等于当前版本判断历史可撤销性。同计划后续按期还款、引用相同资金的其他计划操作、后续退款或期次调整均可能构成依赖，未解除时明确拒绝。后继专门撤销后，前序若状态和资金签名匹配即可再撤销；不得被单纯版本递增锁死。

专门撤销按期操作删除/作废本次转账和新费用、恢复原费用绑定与计划日期、恢复所选期次及原债务归属，再统一核验资金与余额；已发生旧费用不删除。撤销后的已到期费用仍按原日期补齐，原账期已封账时回到待处理，不能自动改日。普通 `repayment` 的 `Reverse` 补齐与 `guardSettlementFunds` 一致的后继检查，避免通过另一删除路径破坏后来偿付。

替代方案是仅校验全计划版本或恢复整个快照。版本方案不支持多次逆序，整快照方案会抹去无关后续记录，因此使用目标状态、来源签名与依赖校验。

### 7. 前端移除功能与同版本契约切换

`RecordPanels.tsx` 的计划详情增加按期入口与还到期次选择；`LiabilityDialogs.tsx`、`SettlementFields.tsx` 替换为统一报价，保留合计突出、手续费小字的两行展示。取消手续费单独输入、结清额外费用和不同费用付款账户、暂不分配选项及抵扣减项，显示唯一还款账户和锁定总额。

期次范围、账户或日期变化使 quote 失效，提交前必须完成当前选择的报价；重试沿用 request key，实质输入变化生成新 key。请求中禁止用户改合计，后端冲突后清除报价并重新核对。细节状态仅以最终服务端结果刷新，不提前把未发生手续费加入当前欠款。

删除 `LiabilitySummary`、`LiabilityDetail`、`PaymentHistory` 的待抵扣与溢缴内容，移除 `TxnFormModal` 中超额可暂存说明；退款表单显示真实到账及可冲减限制，普通还款提示分期须整期。清理 `api/liability.ts`、`liability-inputs.ts`、`liability-client.ts` 和 dialog intent 类型。新后端不兼容旧金额契约，前后端同步发布；数据库旧审计字段不因 API 移除而删除。

## Risks / Trade-offs

- [旧未分配资金真实存在，即使账户余额为负] → 切换前逐有效来源只读核验，任何非零余额阻止启用；保留原记录，先按实际偿付或实际返还处理。
- [统一仓储每笔创建会重分配，复合操作出现临时余款或旧分配变化] → 锁内固定操作前报价和 targets，完整操作完成后才校验，不按中间剩余金额减少本次付款。
- [普通转账/自动事件绕过服务入口] → 在所有外层财务事务执行最终规则，增加通用写入和定时事件的回归，不能仅测新 API。
- [并发还款未改变计划版本] → 报价签名包括真实债务与费用状态，锁内重算，冲突完整回滚。
- [严格移除余款使过去可记录的信用账户溢缴退款不再支持] → 明确拒绝并保留资金事实；只有真实资产到账才能改目的账户，不自动重路由。
- [新分配让已偿付期次再次出现部分余额] → 固定操作目标并保留历史来源，重分配、修改、删除都检查整期结果和依赖。
- [回滚到旧程序不认识按期还款结果或再次收取费用] → 保留关联与审计字段，新代码运行且已有操作后不能直接降级；需先合法逆序撤销相关新操作，或保留兼容读写保护，再执行回滚。
- [工作区另有基金账户规划与已有 API 修改] → 实施只修改本变更所需部分，使用统一的可支付资产筛选，保留他人改动。

## Migration Plan

1. 实施前提供只读核验命令，按有效 credit 与 allocations 算真实剩余，不按账户正余额判断；同时报告本金为零仅剩费用、阻塞手续费和待核对计划等需核对状态。
2. 对非零历史未分配余额，不做自动 SQL 清零。利用旧规则下的合法核对路径，先明确真实偿付已有欠款，或记录实际已发生的负债到资产返还并把真实余额完整关联到返还明细；若现实没有返还，不得为升级虚构。核验报告归零后才继续切换。
3. 本设计复用现有表、字符串操作种类及 JSON 快照，不预设新增数据库表或删除旧字段。若实施确需持久化字段，使用当时下一可用编号的成对迁移，测试正反迁移及新记录保留；不得仅为移除 UI 删除审计字段。
4. 使用本机 MySQL/Redis 与独立测试数据库验证；前后端同步发布新契约，部署前备份财务数据并再次核验。失败留在旧规则，不允许部分账户或不同入口混用两种资金策略。
5. 切换后保留旧操作的只读历史和幂等结果；新请求全部受完整资金分配和整期约束。验证余额、应还、未来计划、费用统计、历史引用与提醒。
6. 若仅发布前发现问题，回退应用文件并保持原数据；若已执行新按期操作，不能直接用旧程序恢复写入。先保留兼容保护或按依赖合法撤销新操作，确认费用绑定、资金不变量及历史核验后再回退。禁止以删真实流水作为快捷回滚。
