## Context

动机和用户确认的行为见 `proposal.md` 与 `specs/vouchers/spec.md`。需要改变的现状：

- `backend/internal/model/transaction.go` 只有 `expense/income/transfer/refund` 四种 `kind`，`entry_date` 决定资金日期与消费日期，`period_key` 写入时物化。普通退款已经支持跨期、关联和部分退款。
- `AccountRepo.List` 与 `StatsRepo.DailyAccountNets` 按 `kind` 算资金；`StatsRepo.DailyTotals/CategoryTotals/PeriodTotals/SumByPeriod` 与 `BudgetRepo.ConsumptionByRoot` 按 `kind` 算消费。首页、总预算、超支评估与封账预览分别复用这些查询，不能只改一条聚合。
- `TransactionService` 已有权限、叶子分类、金额与封账校验及 `OnWrite/OnWritePeriod`，但写钩子立即执行。各仓储构造器接受 `*gorm.DB`，可以绑定同一数据库事务。
- `backend/cmd/server/main.go` 已有周期记账定时器；`AppShell.tsx` 与 `useEnsureRecurring` 已有打开应用补齐机制。既有周期规则会跳过封账期，这个跳过策略不能用于券退款，否则剩余款会丢失。
- 流水改删权限：管理员/记账员可改全部，普通成员仅自己创建，只读不可写；所有角色查看共享账本。周期模板的属主限制不同，不直接复用模板管理权限。
- 最新迁移为 `000004_refund`；生产 MySQL，仓储测试使用真实 SQLite。`txn_export.go` 的原金额列按 `kind` 带正负号，新增解释列须保留该列兼容性。当前没有持久化收支封账快照。

## Goals / Non-Goals

**Goals:**

- 券服务封装数量、成本、生命周期与幂等，外部调用不需要组合多笔流水。
- 资金口径与消费口径只定义一次，所有聚合、DTO、导出有同一组规则和回归用例。
- 数据库提交券操作与其流水后，才失效缓存与重估预算；并发或重试不重复结算。
- 迁移给存量记录设普通用途，不修改其金额、日期、账期、关联或统计。

**Non-Goals:**

- 不把全部账本改成多分录会计系统，不增加隐藏券账户，不重写账户余额存储方式。
- 不引入消息队列、外部退款调用、独立调度服务或前端自动计算财务金额。
- 第一版业务边界见 proposal；过期异常在券页可见，不扩展通知枚举和推送渠道。

## Decisions

### D1：券与操作记录是领域主入口，流水是账务投影

新增 `vouchers` 与 `voucher_events`，模型、仓储和服务放在现有对应目录，新增 `VoucherService` 为唯一券写入口。

`vouchers`：名称、可选平台/商家和备注、`paid_amount`、`purchase_date`、`account_id`、`category_id`、`total_units`、可空 `expires_on`、`auto_refund_enabled`、`auto_refund_suspended`、`schedule_version`、`created_by`、`create_request_key/create_payload_hash`、最后处理错误/尝试时间、时间戳及逻辑删除信息。购券创建键按 `(created_by, create_request_key)` 唯一，防止重试创建两张不同 id 的券；创建载荷摘要保留原值，不因后续编辑而改变。数量使用有范围校验的正整数；金额沿用现有 CNY 上限及两位小数。

`voucher_events`：`voucher_id`、递增操作顺序、`action=purchase/redeem/refund/writeoff`、本操作 `units/amount/entry_date/period_key`、账户/分类快照、`created_by`、`source=manual/auto`、非空幂等键及规范化请求载荷摘要、可空 `schedule_version`、`voided_at/voided_by`。建立 `(voucher_id, request_key)` 唯一键，自动幂等键为 `auto:<schedule_version>`。购买是第一条事件；所有后续事件保存当时成本与日期，撤销保留事件、移除有效账务投影。金额为零的核销保留事件，省略流水。

剩余次数、剩余成本与核销/退款/作废合计从未撤销事件导出；列表通过一组聚合批量查询，避免逐券加载。状态是剩余数量、到期日期、开关、暂停与处理错误的投影，避免持久化相互矛盾的多个状态。

备选：只给普通支出加到期字段不能表达多次核销、剩余成本与撤销；隐含转账到“券账户”会改变现有总资产定义和用户账户列表，因此不采用。

### D2：保留四种 kind，增加服务端赋值的用途

给 `transactions` 增加非空 `purpose`（默认 `regular`）及可空唯一 `voucher_event_id`，用途为 `regular/voucher_purchase/voucher_redemption/voucher_refund/voucher_writeoff`；券 id 可由关联事件解析，避免持久化第二份券关联。新增 `source=voucher_auto`，手动券事件仍为 `manual`，周期仍为 `recurring`。`related_txn_id` 用于券退款指向原购券流水。

| 用途 | kind | 账户资金影响 | 消费支出影响 | 日期 |
|---|---|---:|---:|---|
| 普通支出 | expense | −金额 | +金额 | 普通流水日 |
| 普通退款 | refund | +金额 | −金额 | 到账日 |
| 购券 | expense | −金额 | 0 | 购买日 |
| 券核销 | expense | 0 | +成本 | 核销日 |
| 未用券退款 | refund | +金额 | 0 | 手动退款日/有效期次日 |
| 券作废 | expense | 0 | +成本 | 作废日 |

普通收入与转账沿用现有行为。所有券用途由券服务根据事件类型写入，并验证 kind、用途、来源与事件关联一致；客户端不得配置用途或财务影响。API 读取流水时附用途、券标识、资金影响与消费影响，页面显示业务名称，不暴露数据库术语。

备选：增加多种顶层 kind 会扩展全部类型分支和现有四态表单；两个可自由设置的“影响余额/统计”开关容易组合出非法账务。因此保留 kind，使用有限、内部派生的用途矩阵。

### D3：固定份额成本与逆序撤销，保住分角和历史

金额转换为整数分 `P`，次数 `N`，每份基础成本 `q=P/N` 向下取整，余数 `r=P-q*N` 只分给第 N 份。按操作提交顺序领取连续份额；核销多份累计成本，退剩余/作废一次结算全部未分配份额。费用统一返回 decimal 字符串，不用浮点数。

例如 10 元 3 次为 `333/333/334` 分；先用两次再退剩余，消费 6.66、退款 3.34。零分份额可以核销，有次数事件但不调用正金额流水创建。任意有效状态保持 `已用成本+已退金额+作废成本+剩余成本=P` 和次数守恒。

第一版撤销只允许最后一条有效后续事件，较早事件有后续记录时返回冲突。这样能直接恢复原份额与成本，无需重写其他月份的分角分摊。撤销事件在事务内标记 voided、删除对应投影、恢复剩余；核销/作废只回滚消费，退款回滚资金。自动退款撤销同事务设 `auto_refund_suspended=true`。重复撤销返回已有状态，不再次回滚。

备选：每次按当前余额重新均摊会漂移历史金额；任意顺序撤销再重算后续事件会撞已封账期，因此不采用。操作顺序是提交顺序，不把后续补记日期用于重排既有成本。

### D4：单券事务、行锁与数据库唯一键

每个创建/核销/退款/作废/撤销/修改/删除请求都使用同一 `db.Transaction`。先取得下面定义的账本写锁，再针对既有券锁定券行（生产 `SELECT … FOR UPDATE`），在锁内查询有效事件、校验剩余、权限和封账、保存事件、生成/删除流水，再提交。测试 SQLite 不依赖其实现 MySQL 行锁；生产并发保证另做 MySQL 验证。

所有手动新增操作接受客户端生成的 UUID `request_key`，服务端加 `manual:` 前缀，不接受客户端提供的自动键；客户端重试沿用同一个键，新的明确操作使用新键。购券创建键与事件键分别保证创建/后续操作幂等。先检查既有键及规范化载荷摘要，再校验剩余；重复同载荷返回既有操作（包括已撤销标记），同键不同载荷返回冲突，不修改旧操作。自动操作用 `auto:<schedule_version>`，进程内互斥只用于减少重复扫描，数据库锁和唯一约束提供跨实例保护。核销与退款抢到锁后重读剩余，结清后另一方不得使用过期读取的金额。

仓储在事务中用相同 `*gorm.DB` 构造；从 `TransactionService` 提取可在事务内复用的校验/构建路径，避免普通 Create 提前触发钩子。券服务提交成功后统一失效统计缓存，并为受影响的消费账期触发预算重估；修改购买日期检查原、新两期。提交失败不触发任何成功钩子，通知等旁路失败不回滚已经成功的账务。

已核实 `ClosingService.Close/Reopen` 当前没有与写流水共用的锁，`IsClosed` 一次查询不足以保证封账竞争。采用家庭单账本规模适合的数据库全局写闸门：`000005` 在现有 `settings` 中插入内部 `ledger_write_guard` 行；所有券财务写入、普通流水 Create/Update/Delete/CreateFromRule 及封账/解封在同一事务最先锁该行，随后读取封账状态。统一顺序为账本写锁 → 券行锁（如涉及券）→ 校验和写入，锁持有至提交，禁止先锁券再申请写闸门。ClosingService 同事务写封账状态和审计，取消事务外补偿式删写。这样不增加第三张业务表，封账完成后任何新财务写入只能看到已封状态；写入先提交则封账随后包含其结果。读查询不取该锁。

备选：仅进程互斥不能保护多实例；锁不存在的封账行依赖 MySQL 间隙锁且易出现死锁；单独期锁表增加本项目不需要的复杂度。全局写序列化的代价在自用家庭账本负载内可接受，以 MySQL 封账竞争用例验证。

### D5：自动退款保留计划日期，异常不丢弃

显式加载 `Asia/Shanghai`（生产镜像已有 tzdata），用北京时间日期计算 `expires_on+1`，注入时钟供边界测试。筛选 `expires_on < today`、开关开启、未暂停、仍有剩余的券；事务锁内再次验证版本、有效期与余量。

- 复用现有 cron，增加每分钟扫描；服务启动后执行一次补处理。`POST /vouchers/ensure` 为可记账角色提供打开应用补处理，查询页面对所有角色可读；自动逻辑只允许内部按已保存配置调用。
- 自动退款事件 `entry_date` 固定为有效期次日，用 `PeriodService.KeyForDate` 物化退款账期；`created_by` 取购买创建人，自动来源可辨认，与现有周期生成归属方式一致。
- 已全用、已退款或已作废直接跳过。退款回原账户，该账户停用、计划期封账或数据库错误时整体失败，保持原剩余，记录可展示的错误和尝试时间；不得像周期模板那样永久推进并丢弃封账期。
- 错误状态旁路更新需校验券版本，避免失败扫描覆盖随后成功的用户操作；每轮一个券错误不阻断其他券，下轮重试。列表根据截止日期自然显示“过期待处理”，不依赖后台跑成功。
- 修改有效期或明确重新启用自动退款时增加 `schedule_version`；撤销自动退款只设暂停，不自动重新生成。用户重新启用明确解除暂停、递增版本，下一轮按仍剩余成本处理。

自动记账不证明外部到账，UI 简短显示“按有效期自动记退款”；平台未实际退款可撤销并暂停。无需增加人工二次确认或平台调用。

### D6：全部聚合统一使用资金/消费表达式

在 repository 层维护受控 SQL 片段/查询帮助函数（只接受内部固定表别名），在 model/service 层提供同语义数值映射。不要把客户端可输入字段用于 SQL 表达式插值。

| 路径 | 使用的口径 |
|---|---|
| `AccountRepo.List` | 资金影响；转账保持双边 |
| `StatsRepo.DailyAccountNets` | 资金影响 + 日期，支持资产/负债 |
| `DailyTotals/CategoryTotals/PeriodTotals/SumByPeriod` | 消费影响；普通收入原规则 |
| `BudgetRepo.ConsumptionByRoot` | 消费影响按一级分类上卷 |
| 首页/总预算/封账预览 | 复用以上聚合，不另拼金额公式 |
| DTO、列表、CSV | 同一用途矩阵，显式两种影响 |

券购入及券退款仍存在于流水列表与筛选结果，但消费影响为 0；不得把 `kind=expense` 所有行简单求和当消费。普通退款的负分类、饼图过滤、预算负消耗展示保持既有规则。账户总资产仍是账户余额求和，券金额独立聚合。

### D7：通用接口保护和兼容性

普通 `POST/PUT /transactions` 输入只允许普通业务字段；明确拒绝 reserved 券关联/用途/自动来源字段。服务层修改/删除先检测 `voucher_event_id` 或非普通用途并返回冲突；普通退款关联目标为任何券投影时拒绝，提示去券详情。

购券金额/日期/账户/分类/总次数只在无有效后续事件且原、新购买期开放时可改，原购买投影与分摊同步更新。名称/备注/平台与未来到期配置按购买记录的属主权限改；新有效期不得早于已核销的日期。购买期封账不阻止改未来到期配置，因为不改历史账务。删除无后续有效操作的券时撤销购买投影、逻辑删除券，保留已撤销操作记录以便审计。

普通成员对任何券新增操作使用现有创建流水权限；撤销按目标事件创建人判断；购券信息修改/删除按购买创建人判断。管理员与记账员可管理全部。有效期自动产生的退款归购券创建人，member 可撤销自己的自动退款；viewer 即使直接调用也不能产生用户操作或调用补处理写接口。核销/作废不产生资金变动，可追溯原已停用账户；购券与退款产生资金变动，要求对应账户启用。

CSV 保留原列、金额正负、BOM、CRLF 与公式注入转义，在末尾附用途/券标识/余额影响/消费影响。转账的余额影响列指行的转出账户，转入金额由原“转入账户”列和金额绝对值表达；它的消费影响为零。

### D8：API 与前端切入点

新增 `/api/v1/vouchers`：

- `GET /vouchers`：筛选、分页与全部未用金额汇总（总览汇总不随当前分页变化）；`GET /vouchers/:id`：详情、事件、可操作权限、成本分解。
- `POST /vouchers`：购券；`PUT /vouchers/:id`：按规则更新；`DELETE /vouchers/:id`：受约束删除。
- `POST /vouchers/:id/redeem`：日期/次数/幂等键；`POST /vouchers/:id/refund`、`POST /vouchers/:id/writeoff`：日期/幂等键，金额和剩余份数由服务端算。
- `POST /vouchers/:id/events/:eventId/undo`：撤销；`POST /vouchers/ensure`：到期处理，返回处理数和失败数。静态 `/ensure` 路由避免与 id 参数冲突。

复用现有响应结构：无效输入 400、越权 403、不存在 404、封账/已结清/后续操作等状态冲突 409。自动处理单项错误在券详情持久化展示，接口不把一项错误伪装成全部处理失败。

前端新增 `Vouchers.tsx`、券详情/操作表单和共用购券表单，`App.tsx` 接 `/vouchers`。`Mine.tsx` 放所有查看角色可见入口，避免沿用仅 `canRecord` 的整个卡片门禁；购券/核销等按钮单独按权限控制。`TxnFormModal` 的新建模式提供购券入口并调用同一购券表单，普通编辑不允许切换成券；不新增主 Tab。显示最终分摊和剩余金额只读预览，服务端结果是权威。

`api/types.ts/hooks.ts` 增加券请求、日期与金额字符串、用途/来源、动作权限、失败/暂停状态；券写入和 ensure 成功后统一刷新 `vouchers`、`txns`、`accounts`、`stats`、`budgets`。`AppShell` 在可记账用户打开应用时 ensure 并刷新，后台自动处理后的页面查询遵循现有重新获取机制。首页显示独立未用金额和同口径消费，不把结余解释成余额净流入。

## Risks / Trade-offs

- [所有 kind 聚合漏改一处会重复扣款或出现虚假负消费] → 统一用途矩阵，并用同一完整券生命周期数据验证所有仓储查询、预算、封账、CSV；保留普通退款回归。
- [分摊与撤销重排会改写历史] → 固定份额、最后份承差、仅逆序撤销；用户可查看操作依赖，不能静默更改后续事件。
- [系统按配置先记退款，平台实际未退] → 自动来源可辨认，支持撤销并暂停；这是用户明确选择的自动记账规则。
- [封账/停用账户使补处理不能完成] → 待处理保留全额，页面展示原因，条件解除后按原日期重试；不替用户解封或换账户。
- [SQLite 测试不能证明 MySQL 行锁、ENUM 与唯一索引行为] → 逻辑与聚合用 SQLite；迁移、双实例退款、核销/退款及封账竞争使用隔离 MySQL 实例验证。
- [服务降级到旧版后把券投影当普通支出] → 不能在留有有效券投影时只回退应用二进制；上线先禁用券写入和自动扫描，必要回滚恢复上线前数据库备份并同步应用。
- [既有预算提醒不会因撤销而消失] → 继续遵守同账期同预算一次提醒规则，撤销修正实际消耗，不新增“撤销超支通知”行为。
