## Context

动机与产品范围见 `proposal.md`。访谈中的 Q1–Q12 已确认；用户明确这是没有任何流水的新项目，故采用零余额启用，不建立历史欠款接入流程。

现状约束：

- `backend/internal/model/account.go` 只有 `asset/liability` 和 `repayment_day`，后者校验为 1–28。余额由 `AccountRepo.List()` 聚合，不落库。
- `model.Transaction.Effects()` 已区分资金影响与消费影响。券购入改变资金但不立即计普通消费；券核销和作废计消费但不再扣款。必须沿用这一口径，不能按 `kind=expense` 重算所有欠款。
- `TransactionService.write()/bound()` 与封账通过 `repository.LedgerWrite` 锁同一账本行。券服务也取得此锁，但其 `writeProjection` 直接写 TransactionRepo，不能仅在普通记账服务挂钩。
- `period_key` 表示账本收支账期；负债账单必须有独立周期和标识。实际退款计到账日，历史封账不阻止新增当前退款。
- `NotificationService.EvaluateRepayment()` 目前以全部负余额与本月还款日生成提醒，且按账户月份去重。需要整体改为账单驱动。
- `/accounts` 当前为管理员管理页，API 全员可读；新增全员负债详情入口，不改变账户设置权限。权限采用 `CanCreateTransaction` 和 `CanModifyTransaction`，不是周期模板的归属矩阵。
- 当前迁移到 `000007`，数据库为 MySQL，金额 `DECIMAL(12,2)`。`transactions.source` 是包含 `manual/recurring/voucher_auto` 的 ENUM。
- `add-vouchers` 和 `add-voucher-platform-options` 已完成而尚未归档；前者的 accounts delta 与本变更重叠，归档时需逐条合并，不能丢失券行为。

## Goals / Non-Goals

**Goals:**

- 为全部资金入口建立同一负债投影，账单、分配与流水在同一事务提交。
- 把已经发生的资金、负债本金和未来费用计划分开存储，建立可核验的金额恒等式。
- 用确定的日期及分摊规则覆盖月底、闰年、跨月、部分还款和补齐场景。
- 让管理入口与普通记账入口共用校验和既有权限，保留原账单快照及修正历史。

**Non-Goals:**

- 不替换现有账本的金额影响模型、收支账期、预算、券或封账模块。
- 不引入平台 SDK、外部同步、任意利息计算器或通用事件总线。
- 不为用户不存在的历史流水构建迁移向导；结构迁移仍须保留真实数据库数据。

## Decisions

### D1. 资金流水是唯一余额来源，负债模块管理债务分解

保持四类流水和 `purpose` 语义。分期原消费是一次普通支出，分期费用是独立普通支出，本金还款是普通转账；出账与本金期次不再写资金流水。

新增负债模块，公开面向服务编排的能力：读取汇总与账单、处理资金变动、安排或调整本金、分配抵扣、补齐、核对和结清。内部欠款与分配算法不暴露给 handler 或前端。模块事务绑定后才能写入，普通流水服务、周期生成、券资金投影和分期费用统一调用事务内的资金变动协调入口。

协调入口读取修改前后完整流水及双方账户，分别计算 `Effects()` 和转入侧资金影响：负资金影响产生欠款；正资金影响产生资金抵扣；零影响不产生本金。更新跨账户或改种类时先撤销旧投影，再应用新投影，显式分配策略保留并重新校验。不能只监听提交后的 `OnWrite`，也不能使用全局 GORM 回调暗中做账。

费用关联通过专用计划/操作关联表达，`purpose` 仍为 `regular`。当前 `IsVoucher()` 将所有非 regular purpose 视为券，直接添加费用 purpose 会误触券保护；因此不复用该字段。自动费用增加 `source=liability_auto`，迁移扩展 ENUM 并保留原值，前端过滤及标签同步支持。

备选方案是按总负余额推算本期欠款或为每期本金生成支出；两者分别无法区分到期债务、会重复扣款，均不采用。

### D2. 账单规则版本化，周期边界和到期日持久化

账户新增子类型与是否完成账单设置；规则独立记录版本、账单日、还款日、月份偏移、生效日期，原 `repayment_day` 作为账户当前有效规则的兼容展示字段，所有设置写入通过同一入口完成，禁止两处分别修改。

以账本时区的日历日期计算，调用方显式传入时钟，不按 24 小时时差或 UTC 月份推导日期。账单日当天包含在该期，自动出账在次日开始后进行。同月还款实际日期必须晚于实际账单日，按短月取月底之后再次校验；例如两者短月都变为月底时，同月组合不可用，应选次月。

首个周期从规则启用时所在自然账单区间开始，只接纳实际已有来源，不生成启用前的空白历史账单。规则变化在当前旧规则周期结束后的次日生效；新周期从该日起到新规则的下一个有效账单日，后续按新规则连续计算。每份已生成账单保存区间、日期、规则版本和快照，不能套用当前账户规则重新解释历史。

已有未来分期的尚未出账本金期次随新规则重新定位到顺序相同的未来账单，费用日期只在用户明确选择跟随规则时调整；已发生费用、已出账本金与手工指定归属不变。调整列出预览与操作记录。

备选是复用 `PeriodService.Range()` 和 `period_key`；它用于账本收支且历史区间按当前规则换算，不适合作为负债账单标识和历史边界。

### D3. 数据模型围绕来源、欠款、抵扣和计划组织

新增表的主键采用现有 bigint，金额全部 decimal，外键保护财务历史。具体列名以以下模型作为实现契约：

| 资源 | 关键内容及约束 |
| --- | --- |
| 账户扩展 | `liability_type`、`billing_enabled`；资产不接受负债规则，受管理负债从零启用；余额继续不落库 |
| `liability_bill_rules` | account、version、statement_day、repayment_day、repayment_month_offset、effective_from；同账户版本唯一 |
| `liability_statements` | account、kind（月度/结清）、唯一 bill_key、rule_version、cycle_start/end、due_date、issued_at、出账快照、参考金额、核对状态；月度键按账户与 cycle_end，结清键按操作标识 |
| `liability_debt_items` | account、来源流水、本金或费用类别、可选 plan/term、目标账单、原始金额、修正版本；同一有效来源分片唯一 |
| `liability_credit_events` | account、来源资金流水及账户侧、额度、默认/指定/保留策略、实际日期；同来源账户侧唯一 |
| `liability_allocations` | credit_event、debt_item、amount、策略、操作标识、有效/已撤销；分配总额不得超过抵扣或欠款，撤销有来源记录 |
| `installment_plans` | 原消费、account、principal、term_count、first_statement、手续费模式和输入、费用账户及分类、created_by、版本、状态 |
| `installment_terms` | plan、期号、本金、目标账单、费用金额/日期、唯一费用流水关联、发生/待处理/取消状态；plan 与期号唯一 |
| `liability_operations` | 操作类型、actor、request_key、输入摘要、关联资源、前后快照、原因、修正关系、结果；用户操作按 actor 与 key 唯一，系统操作有稳定 key |
| 提醒扩展 | 可空 statement_id、dedup_key 与 resolved_at；新还款提醒 dedup_key 唯一，其他提醒旧字段和行为保留 |

账单原出账快照不覆盖；可变的当前应还通过有效欠款及分配计算，补记、调归属、退款等操作附加修正记录并使核对状态失效。分期将原消费的一份本金欠款重排为 N 份，其总额不变，不能让原始普通欠款与分片同时有效。

普通流水删除仍遵循现有协议；负债来源关系在事务内撤销并留操作快照，不以限制性外键让本来允许删除的普通流水无法删除。受管理分期及结清来源不允许直接删除，专门撤销流程保留原操作快照。来源已合法删除时，可空外键加不可变原始标识保留审计追溯。

备选是只给流水增加 statement_id；单一字段无法表达多期分摊、一笔还款抵多账单、资金余量和费用生成幂等，因此采用独立关联资源。

### D4. 金额恒等式与确定性分配

所有校验和计算使用 decimal 或整数分，前端只显示字符串金额。

定义已保存资金流水对应的实际入账资源（沿用现有账户聚合口径，手工预填未来日期的流水仍属于已保存来源；未来费用计划尚未生成流水，因此不在其中）：

- `I`：已出账明细未被抵扣的欠款之和，含逾期。
- `U`：尚未出账明细未被抵扣的欠款之和，包含全部未出账分期本金。
- `F`：未出账分期本金，为 `U` 的子集，不再次相加。
- `C`：真实正资金事件中未分配部分，含预还款和退款余款。
- `B`：既有账户聚合余额。

零余额启用的受管理账户必须始终满足：`B = C - I - U`、`total_debt = max(-B, 0)`、`surplus = max(B, 0)`。未来费用预估不进入任何一项。后台写入后校验相关资源，测试以独立流水余额计算核对该恒等式。发现投影差异拒绝提交，不能把差额藏入一张虚拟账单。

“本期应还”取最近的尚未逾期待还到期日所对应账单剩余额；“逾期应还”单列所有过期未还额。任何手工账单参考金额都不能替代真实资源计算。

自动还款以 `(due_date, statement_id, debt_item_id)` 排序，先过期再未过期的已出账欠款。指定分配验证同账户和正金额，其余可明确保留待抵扣，或按用户选择继续自动分配。待抵扣在后续普通消费和新出账时使用，不能提前取消未来分期；提前结清是允许指定未来本金的独立操作。

例：I=1000、U=2000，转入 1200 后 I=0、U=2000、C=200，B=-1800。下一期 1000 出账时自动使用 C=200，剩余应还 800，B 仍为 -1800。这个过程只重新分配资金，没有新转账或新消费。

转账从受管理负债转出也会产生真实欠款明细；转入形成资金抵扣，两端均处理。这里只保持现有通用转账的余额一致性，不增加现金借款业务或计息。

### D5. 手填费用按真实收取日期入账

计划只能选择以下一种模式：`per_term`（每期金额）、`total_spread`（合计金额分摊）或 `upfront`（一次收）。每期固定金额的合计为期数乘输入；总费用和本金分摊采用整数分向下取整，末期补尾差。允许费用为零，生成时跳过零金额流水；本金期次必须全部大于零。

每期金额、日期、费用账户和分类存入期次。费用日期默认对应账单日，用户可填写实际日期；负债支付归入指定账单，资产支付只扣资产。一次性费用按用户所填实际日期入账，其创建请求与原消费/计划在同一事务内提交；未来日期只存计划。

`EnsureDue(now)` 顺序为：补普通周期及券资金事件 → 为已到期计划生成费用 → 形成结束周期账单 → 分配既有余款 → 评估还款提醒。复用现有进程 cron，每 5 分钟补齐并在每日 08:00 提醒前调用；启动和 AppShell 打开也补齐。每个独立费用和账单在共享锁中短事务处理，避免跨多年补齐占用一把长锁。

费用唯一键由计划与期号组成；自动 actor 为计划创建人，系统执行既已授权计划，不因仅负责触发补齐的查看者身份改变归属。补齐日期封账、费用账户不满足操作条件、分类失效等错误保留可见的待处理状态；不擅自迁移日期、不解封、不当作已发生费用。停用负债禁止新消费和新计划，但专用执行入口可处理既有费用及还款，校验不因前端隐藏而放松。

如果某笔未来费用提前被用户手工记账，必须从期次入口关联已有费用流水，而不是再生成一笔。已发生费用只能通过合规修正或退款改变；未来费用可取消。

备选是计划创建即把所有费用计入余额，或在用户还款时把手续费混入本金；前者提前记支出，后者不可区分费用发生日，均不采用。

### D6. 核对、退款与结清只改变有依据的资源

核对保存可选平台参考金额，不写入财务余额。差异通过真实漏记资金、费用或账单归属修正；只有差异为零且无未处理费用/分期问题时，才允许标记已核对。出账后修改来源时保留原快照、修正差额与新的核对状态。

已有消费转分期只重排经核对的未还本金，已经还款和实际退款仍保留原历史分配；已出账来源的重排记录账单修正。消费本金总额、已还/已退部分与新未来计划合计必须保持一致，不能再为已还部分生成待还期次。

普通同账户关联退款优先抵原消费的未还本金，再处理余款；已还原消费不撤销历史还款，退款是新的正资金事件。退款到其他账户不抵原负债。分期退款入账后先抵对应本金，后续期次标记待核对；用户按平台真实规则填写剩余安排，合计必须等于退款和已还后的本金，费用退回需要另一笔明确退款。费用不明的计划维持待核对状态，金额界面不伪装成已确认。

结清预览捕获资源版本和实际本金；提交在锁内重新校验，不能利用客户端旧预览降低金额。本金与平台金额有差异时先做真实退款或补记；资金充足的真实抵扣可以用于结清，仍欠部分产生转账。已发生未付费用与结清费显式列入支付，若费用计入负债，则先记费用支出再将相应偿付纳入转账；若从资产直接扣费，则另记费用支出，不能两边同时记同一费用。

结清的未来本金期次转为由结清分配覆盖，不再在后续账单重复出账；未发生费用取消。结清组合全部成功后才标记 settled。修正/撤销专用入口校验每笔组成流水的权限和封账状态，按逆向操作恢复有效计划及抵扣，原记录保留；若已经封账则拒绝修改该资金流水，提示走既有解封或真实新退款流程。

备选是直接将未来本金与费用归零，无法区分债务是否真实偿还，故禁止。

### D7. 共享事务、角色与重试校验

结清时，将已由真实资金覆盖但尚未出账的本金明细归入独立结清单，保留欠款和抵扣标识；后续月度账单不再重复列出这些本金。撤销结清时按操作前快照恢复原账单归属。结清单与月度账单使用不同唯一键，以支持同一天的多次结清，原资金和消费口径不变。

用户复合写入与普通流水写入共用 `LedgerWrite`。已有外层事务内调用事务绑定的 entry writer 和负债模块，不重新进入公共 Create 方法形成嵌套锁；`TransactionService.bound()` 需要重新绑定新增依赖，VoucherService 的直接投影写入也调用同一协调入口。

校验顺序为身份与来源权限、请求幂等、账户规则及状态、资源版本和金额、相关资金流水封账、资金与投影写入、审计、金额恒等式。只有提交后触发统计、预算和前端查询缓存失效；当前账单提醒金额与解决状态在同一事务更新，定时评估补充时间导致的状态变化。

创建自己的还款可分配到其他成员创建的欠款，这属于新资金操作；修改他人的消费、计划或还款分配仍须 `CanModifyTransaction`。生成的费用按计划创建人归属，记账员可以按流水矩阵管理全部。复合操作逐一验证受修改来源，不能仅验证最外层计划 owner。

客户端请求标识和输入摘要保存在 operations：相同 actor/key 与相同内容返回已提交结果，不重复写；相同 key 不同内容返回 409。先验证可查看目标和请求 actor，避免通过重试读到别人的操作结果。系统键按费用期次或账单周期构造并由数据库唯一约束兜底。

纯账单归属或分配修正以新的操作记录改变当前应还，不改动历史封账资金流水或原出账快照；若需要修改实际流水，仍要求该流水的旧、新账本账期均开放。已有退款和券的直接改删限制保持。

备选是各 handler 分别写转账、账单和分配，任何中途失败都可能使余额与应还不一致，因此不采用。

### D8. 还款提醒以账单为对象

提醒查询已出账、未还大于零的账单，使用其冻结到期日，日期窗口为提前 3 天含当天，次日开始逾期。去重键为 `repayment_due:statement:{id}`，不再按账户月份。payload 保存初始触发信息和当前剩余金额、状态；新增 statement_id、resolved_at 和可空唯一 dedup_key 支持关联与未读查询。

普通评估只更新现有提醒，不每日增加未读；已还置 resolved 并退出未读待办，历史详情保留。合法撤销使账单重新应还时重新激活且只标未读一次。read_at 与 resolved_at 分开表达“看过”与“已解决”，预算和周期提醒保持原行为。停用账户不新建还款提醒，但详情仍展示真实欠款。

备选是继续更新账户总欠款提醒，仍会把未出账当作到期债务，故以账单标识替代。

### D9. API 与用户流程

扩展现有账户 DTO 和流水 DTO，金额统一字符串；流水附加只读的账单/plan/term/operation/repayment 关联，不让普通写入请求伪造生成费用来源。API 沿用 `/api/v1` 和现有 response/错误约定：输入错误为 400，越权 403，资源不存在 404，封账、受管理资源直改、版本冲突和幂等冲突为 409。

| API | 行为与权限 |
| --- | --- |
| `GET /liabilities` | 全员读取负债汇总、下一到期与逾期额 |
| `GET /accounts/liability-types` | 全员读取数据库中的消费信用类型、名称和排序；配置校验使用同一目录 |
| `GET /accounts/:id/liability` | 全员读取账户规则、金额分解、账单/分期与问题状态 |
| `PUT /accounts/:id/liability-settings` | 管理员配置子类型、周期与规则生效版本 |
| `GET /accounts/:id/statements`、`GET /statements/:id` | 全员读取账单列表与来源、分配、快照和修正 |
| `POST /liabilities/ensure` | 任意登录用户触发已经授权的系统幂等补齐，不允许携带手工写账参数 |
| `POST /statements/:id/reconcile` | 可记账角色保存参考核对结果，变更来源时逐条校验写权限 |
| `POST /liabilities/repayments` | 可记账角色新建转账及默认或指定分配 |
| `PUT /liabilities/repayments/:id/allocations` | 按原转账属主矩阵重新分配，留修正记录 |
| `POST /liabilities/installments` | 同时创建一次消费及计划，或将有权管理的消费转分期 |
| `GET /liabilities/installments/:id`、`PATCH /liabilities/installments/:id` | 全员读；更新未来计划按来源流水权限 |
| `POST /liabilities/installments/:id/refund-adjustments` | 引用实际退款记录，核对并调整未来本金和费用 |
| `POST /liabilities/installments/:id/settlement-preview`、`POST /liabilities/installments/:id/settle` | 预览与带请求标识提交结清，提交校验所有组成资源 |
| `POST /liabilities/operations/:id/reverse` | 专用合法修正/撤销，按组成流水权限和封账约束执行 |

`/accounts` 保持管理员设置页，增加规则表单和详情链接；新增全员 `/liabilities` 及 `/liabilities/:id`，在“我的”提供查看入口。详情头部展示总欠款、最近到期应还/日期和逾期，账单与分期使用平铺列表或标签切换；分期本金为未出账子项，未来手续费带“预估”标记。待配置、待核对、费用阻塞与已解决提醒有明确状态。

还款表单预填最近应还，显示资金账户、日期、金额、分配预览和剩余待抵扣；费用与本金分行展示。分期表单支持三种费额模式、费用账户/分类/日期、各期预览和尾差。退款沿用现有入口，涉及分期时链接后续核对，不强迫重填一笔已到账退款。结清先显示本金和费用，再提交一组操作，避免用户重复记账。

写入提交后统一失效 accounts、liabilities、statements、installments、transactions、stats、budgets、notifications 查询；纯 metadata 变动不触发重复资金写入。桌面及移动端使用同一 DTO 与权限判断。

## Risks / Trade-offs

- [平台入账日与消费日不同] → 默认按消费日期计算，提供独立账单归属调整和平台参考金额核对，不声称自动账单等于官方账单。
- [分期未来本金与预还资金同时存在导致误解] → 保持 `B=C-I-U`，将 F 明确标为 U 子项，待抵扣金额独立显示。
- [手续费发生日封账或配置失效] → 费用生成保持未完成且可见，账单不得标记核对完成，修复后幂等补齐，不改历史日期。
- [多入口遗漏负债投影] → 普通、周期、券、自动费、转账双方均接共享协调入口；集成测试逐入口对比既有余额聚合。
- [还款、退款和结清并发] → 共用账本锁、资源版本与唯一键，原子更新并在失败时验证零副作用。
- [归属调整影响已有抵扣] → 保留手动意图，自动重校验只处理受影响来源，记录撤销和重新分配，不静默重排无关还款。
- [全账本锁影响批量补齐耗时] → 每个费用/账单使用短事务，按到期资源索引扫描，详情批量聚合而非每行查询。
- [已完成券 change 尚未同步主规格] → 按已实现的资金影响开发，归档时合并重叠 accounts/transactions 块，回归券测试；本次不自动归档其他 change。

## Migration Plan

个人负债归属补充：`000011_personal_liability_accounts` 为负债账户持久化 owner_id，全部个人负债读写按登录用户校验，管理员不跨越此边界。一个用户可持有多份同类型账户，各自已有独立账单规则。账户资料创建和日期设置为登录账号自助能力，财务写入沿用角色资格；资产账户仍按原管理员设置权限。新用户首次访问从数据库中 default_account 类型模板建立个人默认账户，用户初始化标记在财务共享锁内持久化，防止并发复制或删除后重建。旧账户按单一历史记账人归属，否则归初始管理员，保持主键、余额、账单、流水不变。个人关联流水和导出、账单/计划/操作、提醒、资产明细及负债付款券/周期都检查此归属；登录身份改变时清理前端缓存。

1. 在当前 `000007` 后新增顺序 up/down 迁移：账户字段、规则及关联表、提醒字段/索引，保留并扩展 transactions.source ENUM。新增表先有索引与唯一约束，后部署依赖它们的服务。
2. 对现有默认零余额信用卡只标记待配置，不猜测账单日；不插入历史账单，不改任何流水、余额或其他账户。全新初始化种子保持零余额与待配置状态。
   `000009_default_credit_accounts_and_platforms` 在既有账本补齐花呗、京东白条、抖音月付、美团月付，空库同时初始化原五个账户。按名称缺失插入，保留已有同名账户的类型、余额、状态及规则。预置支付宝、微信、淘宝、天猫、京东、拼多多、抖音、美团、饿了么，目录同名精确复用。`000010_database_catalogs` 创建消费信用类型目录、初始化空库分类；移除 Go 中重复的默认账户、平台、分类种子及类型清单。启动只保留环境配置驱动的初始管理员创建。字典读取、配置校验和前端选项/标签统一查询数据库，新增消费信用类型不要求修改应用代码。两个数据迁移的 down 均保留数据；字典表也保留，避免丢失已自定义的名称。
3. 部署后管理员为实际消费信用账户配置规则；账户设置只在零余额且无无法归属流水时启用。若检测到用户声明外的旧数据，明确报错并保留数据，不能清库或临时拼凑接入算法。
4. 用空库初始化、仅有默认账户库结构升级、MySQL 唯一键/外键及模拟并发写入验证迁移；SQLite 用于业务集成测试，不能替代 MySQL 迁移验证。
5. 结构尚无负债业务数据时可以执行 down；已有分期、费用或账单数据后，down 必须拒绝破坏性回退，不将 `liability_auto` 费用伪装为 manual，也不丢弃关联。需要回退服务时保留新结构并使用能识别新来源的兼容服务版本。
6. 实施完成后运行后端 gofmt、go vet、go test，前端 build 与对应 E2E。本阶段只校验规划文档，不部署或修改业务代码。
